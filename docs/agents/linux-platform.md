# linux platform lane

- **Scope**: `src/platform/linux/` — GTK3 + WebKitGTK over `bun:ffi`, a C shim compiled at launch. Written on macOS and then proven on `ubuntu-sandbox` under Xvfb (Ubuntu 25.10 aarch64, real `libgtk-3.so.0` + `libwebkit2gtk-4.1.so.0`), so the claims below are measured there and the platform is no longer a header reading.
- **Files**: `shim/{10_prelude,30_webview,40_window,50_pump}.c` (one job each), `shim-source.ts` (assembles them into one TU as text), `shim-ffi.ts` (`cc()` + the hand-written `LinuxShim` argument contract), `cstring.ts` (the NUL-terminated buffer every `cstring` argument needs), `backend.ts` (`LinuxBackend` seam + `createGtkBackend`), `platform.ts` (class + `createPlatform`), `preflight.ts`, `index.ts` (barrel).
- **The seam**: `createPlatform(config: CrustConfig, backend: LinuxBackend = createGtkBackend())` — the default argument evaluates `createGtkBackend()` at call time and loads nothing, so constructing a `LinuxPlatform` on macOS is safe and a test can inject a fake and never touch GTK.
- **No `#include` in the shim, no `-l` flag in `cc()`**: every GTK/WebKit symbol is a hand-written prototype resolved through C-side `dlopen`/`dlsym`, so the unit links libc only and a missing library is a returned message instead of a load-time failure.
- **Trap — `cc()` still needs `libc.so`, which is a `-dev` file**: the shim links libc, so TinyCC wants the linker script only `glibc-devel`/`libc6-dev` ships, and a runtime-only machine fails `library c not found` on its first command; `linkError` in `preflight.ts` translates that into the install line (2026-11-16).
- **Preflight probes the runtime, not the SDK**: `dlopen("libgtk-3.so.0", { gtk_init_check })` and `dlopen("libwebkit2gtk-4.1.so.0", { webkit_web_view_new })`, because a `-dev` package being installed says nothing about what will load at launch.
- **Decision — no `GtkApplication`**: an application object owns `gtk_main()` and quits when the last window closes, while Bun's main thread owns the loop; the pump is one `g_main_context_iteration(NULL, FALSE)` per `setTimeout` tick, the same shape as the darwin `NSRunLoop` slice.
- **Decision — liveness from a C slot table, not the widget**: `gtk_widget_get_visible` on a destroyed window reads freed memory, so the `destroy` signal flips a flag in a 32-slot table and `shim_window_alive` reads that flag. 32 is the ceiling on simultaneously tracked windows.
- **Trap — gate the library open on a `shim_ready` flag, not on the handles**: a failed `dlsym` leaves both `dlopen` handles non-null, so checking the handles reports success on a retry whose function pointers are still null.
- **MEASURED 2026-11-16 on `ubuntu-sandbox` (Ubuntu 25.10 aarch64, real GTK under Xvfb) — a JavaScript string is never a valid `cstring` argument**: bun:ffi throws `a JavaScript string is not valid here; return it from a 'cstring'-returning callback, or pass a pointer/TypedArray`, which surfaced as `FAIL step 3/6 createWindow`. The declarations were right and two call sites were wrong: `shim_window_new(title)` and `shim_webview_load(web, url)`. The fix is `cstring(value)` — `Buffer.from(value + "\0", "utf8")` — and the trailing NUL is part of the contract, because a buffer without it over-reads.
- **Trap — argument encoding is only testable through an injected symbol table**: `createGtkBackend(symbolsFor)` takes the table, so `backend.test.ts` records what a real GTK would receive and asserts a `Uint8Array` whose last byte is 0, for the title, the URL and an absent title (one NUL byte). A fake `LinuxBackend` cannot see this class of bug because it replaces the FFI call entirely.
- **Trap — `bun:ffi` pointer arguments take `bigint | Pointer | null`, never `number`**: `NativeWindow.win`/`web` are `bigint` and a raw `number` is a type error (`Argument of type 'number' is not assignable to parameter of type 'bigint | TypedArray | Pointer | null'`), so a pointer returned as a number is converted once with `BigInt(Number(...))`.
- **Trap — `WindowsShim` in `src/platform/windows/backend.ts` types its `cstring` arguments as `string`** (reported to the coordinator, not edited): `ffi.ts` declares `CS` for `shim_register_class`, `shim_window_new`, `shim_window_set_title` and `shim_webview_new`, while the C side takes `const char *` and converts to `shim_wchar` itself — so Windows needs the same buffer fix at its own call sites.
- **Trap — `bun run test <path>` does not scope anything**: the `test` script already names `src/bridge src/plugins src/platform …` and bun appends extra args, so the whole suite runs; use `bun test src/platform/linux` for the scoped run.
- **Trap — `bun check <file>` scopes to that file's module graph**, not the repo (`bun check src/app-loop.ts` reported 128 files against 469 repo-wide), which is how to check a shared file without reading another lane's red.
- **Trap — the prelude header comment contains the word `#include`**: assert a directive with `/^\s*#include/m`, not a substring, or the "no headers" test fails on its own explanation.
- **Trap — the prelude forward-declares `shim_pump_resolve`/`shim_gtk_resolve`**: a test matching the bare name `shim_pump` finds the prelude first, so the assembly-order test matches full signatures (`int shim_pump(void)`).
- **Decision — `start()` does not create the configured windows**: `openWindows` in `src/app-loop.ts` is the single place a configured window is created, and pre-creating them in `start()` makes every app throw `window "…" already exists`. `start()` loads GTK and nothing else.
- **REMOVED 2026-11-16 — the `crust://` page-serving scheme**: `35_scheme.c`, `scheme-page.ts` and the `registerScheme`/`register` member of the backend seam are deleted. darwin serves a page only through `-loadRequest:` with the bridge URL (`src/platform/darwin/shim/30_webview.c:27`), `urlScheme` is optional app config with no default, so a framework-owned `crust://` handler collided with an app's own deep links and made Linux the one platform loading pages differently. The webview now navigates on the URL the window was created with, the same value darwin hands to `-loadRequest:`.
- **Tradeoff, recorded not implemented**: an in-memory scheme would let a built app load its embedded assets with no HTTP server and no port, which is cheaper than the bridge. It stays unimplemented because one page-loading path across three platforms is worth more than the port, and because `crust://` is the app's namespace to claim — a future variant needs its own scheme name that is not one an app may own.
- **Dispatch (this lane owns the one-line change)**: `loadPlatform` in `src/app-loop.ts` is a `switch (process.platform)` with `darwin`, `linux`, `win32` arms, each importing its own barrel, and a `default` that throws a named error. The linux arm passes the whole `CrustConfig`; the darwin arm is unchanged in behaviour (`{ appName: config.app.name }`).
- **Dispatch trap — the windows arm needs `appName` added**: `WindowsPlatformConfig` is `{ appName, userDataDir }`, and a bare `CrustConfig` is structurally assignable (all fields optional) while leaving `appName` undefined, which registers every app's window class as `crust`; the arm passes `{ ...config, appName: config.app.name }`.
- **`src/runtime.ts` keeps a darwin-typed variable on purpose**: `nativePlugins` declares its platform parameter as `DarwinPlatform` and reads Darwin-only members, so `loadDarwinPlatform(config)` is selected first on macOS and every other OS goes through `loadPlatform`; `app.attach` takes the wider `Platform`. Widening `nativePlugins` instead would mean editing `src/runtime-plugins.ts`, which is not this lane's file.
- **PROVEN 2026-11-16 on real GTK**: `bun run e2e:linux` → `e2e:linux: PASS 8/8 assertions 5.7s` on `ubuntu-sandbox`, with the unit suite green there (`30 pass, 1 skip`) and the smoke showing a GtkWindow + WebKitWebView shown and loading `about:blank`, 6 main-context slices at 16 ms, `shim_window_alive` still 1 after the pump, and `quit()` exiting 0 from inside the platform.
- **Still unproven**: a loaded document, page JS, an `invoke` round trip, a real bridge URL over HTTP rather than `about:blank`, a user-initiated window close flipping the destroy slot, and Wayland rather than Xvfb/X11.
- **READ FROM CODE, not measured (2026-11-18): the window size floor was one argument and one axis wrong** — `shim_window_new` took only `min_w` and called `gtk_widget_set_size_request(win, min_w, h)`, so the opening height became a permanent height floor and `minHeight` never crossed FFI at all. The shim now takes `(title, w, h, min_w, min_h)` and sends `min_w > 0 ? min_w : -1, min_h > 0 ? min_h : -1`, because `-1` is GTK "no request" while `0` is a real floor of zero. `backend.test.ts` "both minimums reach the shim…" and `shim-source.test.ts` "the window takes both minimums…" pin the call args, the C prototype and the `[CS, I32, I32, I32, I32]` array.

## The browser surface (2026-11-21)

- **A surface is `shim_webview_new()` placed into the window's overlay** — `41_container.c` gives every window one `GtkOverlay` whose main child is the app's own page, so a surface is an overlay child at the rectangle the caller reserved and a move is the same `shim_webview_place` call again.
- **`shim_webview_allocated(web, 0|1)` is what proves a placement took** — `gtk_widget_set_size_request` alone proves a request was made, and GTK's own allocation is the only number that says the overlay actually laid the child out at that size.
- **The two policies are GTK signals, not delegates** — `create` returning NULL refuses a new view (and the URL is read through `webkit_navigation_action_get_request` + `webkit_uri_request_get_uri`), and `permission-request` returning FALSE denies capture, geolocation and clipboard reads outright.
- **`shim_webview_uri`/`is_loading`/`can_go_back`/`can_go_forward` are resolved with `shim_sym_or_null`** — an older WebKitGTK fails one command by name instead of refusing to launch every app, the same rule the proof-only reads already follow.
- **Closing a surface is `gtk_widget_destroy`** — it removes the widget from the overlay itself, so no container keeps a child that is about to be freed; the per-view load record stays keyed to the address and `shim_state_register` resets it when a new view lands there.
- **`capture` has no WebKitGTK path here** — `webkit_web_view_get_snapshot` answers a cairo surface this layer cannot encode, so the adapter answers `not-implemented` naming it rather than a screenshot of the screen.

- **A webview added straight to the window's `GtkOverlay` cannot hold a rectangle** — measured on the ubuntu gate: a 220x120 size request allocated 456x304 and 180x90 allocated 440x288, both exactly the 480x320 window minus the placement's margins, with `hexpand`/`vexpand` already 0 and `halign`/`valign` START. The overlay gives a direct child its leftover area; flags and alignment cannot turn that into a rect. `42_host.c` therefore gives every surface its own `GtkFixed` as the overlay child, puts the webview inside that, and reports the host pointer so a proof can assert the surface's parent is not the window's box.
