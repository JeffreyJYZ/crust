# Lane memory — TypeScript extensions wiring

- Config shape a project writes: `extensions?: string[]` at the root, beside `plugins`; entries resolve against `<project>/extensions`, a bare name gains `.ts`, an absolute path passes through, a `..` climb is refused by `validateExtensions`.
- Root key `extensions` is in `ROOT_KEYS` and validated by `validateExtensions(v, root.extensions)` from `schema.ts`, so an unknown root key still fails and a bad entry reports `extensions[0]`.
- `extensionEntrySource` gained `header?: boolean` (default true) so the wrapper can prepend the import lines without a second `// Generated by crust build` line; its default output is unchanged.
- Generated entry with extensions: import block first, then config/assets/startApp, then `import { extensionRegistry }`, then `const registry = extensionRegistry();` and `registry.register(extension0.default, extension1.default);`, then `registry,` inside the `startApp({…})` call.
- Zero extension files must stay byte-identical: `wrapperSource` appends no extension line and no `registry` key, asserted against the literal pre-change string in `src/cli/build/wrapper.test.ts`.
- Runtime registration point is `startBridgeFor` in `src/runtime.ts`: `(options.registry ?? new PluginRegistry()).register(...selectedPlugins, ...app.plugins(), appPlugin)`, so extensions land in the same table the bridge serves and before `startBridge` is called.
- `extensionRegistry()` lives in `src/extensions/registry.ts` (a fresh `PluginRegistry`), not in `runtime.ts`, so the generated entry imports a small module and the runtime keeps line headroom.
- `StartAppOptions` moved to `src/runtime-options.ts` and is re-exported from `runtime.ts`; runtime.ts went 188 to 176 lines, so the next addition there still fits the 200 cap.
- Trap: `renderExtensionImports` hardcodes the identifier `registry` — the wrapper must name its variable exactly `registry` or the generated line is a ReferenceError.
- Trap: `resolveExtensionFiles({ dir: <project>/extensions })` is the build's resolver, so `extensions/x.ts` resolves through `dir/..` and bare `x.ts` through `dir`; a project-root `ping.ts` is unreachable from config except as an absolute path.
- `crust build` fails with `extensions entry <path> does not exist` for a config-named missing file, and prints `extensions  N file(s) embedded` only when there are any, so a no-extension build's stdout is unchanged too.
- `loadExtensions` is deliberately not called during build: it imports the project's files, and a build should not execute app code to embed it.
- Not wired, out of this slice: `crust dev` does not load extensions from disk, and a single-file build (`buildSingle`) carries none.
- Measured: `bun test src/config src/extensions src/cli/build.test.ts src/cli/build/wrapper.test.ts src/runtime-extensions.test.ts` = 66 pass, 0 fail.
- Trap: a scoped `bun check <files>` still typechecks the import graph, so `src/platform/linux/*` errors appear from a sibling lane; filter with `rg -o 'file="[^"]+"'` before reading a scoped run as red.
- Trap: `bun run test` counts a module that fails to import as a `fail` with no `(fail)` line — read the `N errors` summary and the file list before blaming a test.
- Trap: `src/cli/notarize.test.ts` and `src/cli/package.test.ts` were red from another lane because their fixture writes `windows: []` while `validateWindows` demands a non-empty array — not caused by this wiring.
- Bug fixed 2026-11-16: a default import already binds the module's default export, so `extension0.default` was `undefined` and a built app threw `register: not a plugin definition`; `renderExtensionImports` now emits `registry.register(extension0, …)` and both test files pin that form.
- `src/cli/build/wrapper.test.ts` now executes the generated entry against a stub `startApp` plus the real `extensionRegistry()` and asserts `seen === [["clock"]]` — the only assertion that pins the import shape and the register call together.
- `src/cli/dev/entry.ts:34-40` still carries a comment describing the old divergence and builds its own `extension${index}` list; that lane should drop the comment and call `renderExtensionImports(files)`, whose output is now identical.
- Real proof for the example: `bun src/cli/index.ts build --dir examples/extensions` writes `registry.register(extension0);` into `examples/extensions/dist/crust-entry.ts`, and `bun -e` over that project's `clock.ts` gives `registered: [ "clock" ] commands: [ "now", "startTimer", "stopTimer" ]`.
- Trap: `src/extensions/entry-source.test.ts` also pinned `.default`; a fix to one generated line needs both test files updated or the suite stays red.
- Regression 2026-11-16: a lane ran a bare `bun fmt` (135 files) then `git checkout --` on 118 of them, which reverted `CrustConfig.extensions` in `src/config/types.ts` while `schema.ts` kept its `ROOT_KEYS` entry and `validateExtensions` call — `bun check` then failed at `src/cli/build.ts` and `src/cli/dev.ts` with `Property 'extensions' does not exist on type 'CrustConfig'`.
- Only `types.ts` was lost in that revert: `schema.ts`, `build.ts`, `wrapper.ts`, `runtime.ts`, `runtime-options.ts`, `package.json` exports and every test survived, so restoring one field was the whole fix.
- Rule for this repo: `bun fmt` takes explicit paths, never bare; and a formatting-only diff is kept, never reverted, because a revert destroys other lanes' in-flight passes.
- Extension loading is a hoisted `async function extensionPlugins()` holding `const extensionN = (await import("<abs>")).default;` per file; `renderExtensionImports` emits `registry.register(...(await extensionPlugins()));` and zero files still emits nothing at all.
- A function was chosen over inline `await import` consts because it is inert wherever the wrapper emits it and it keeps `renderExtensionImports(files)` path-free, so `src/cli/dev/entry.ts` needed no change.
- Gap, not mine to close: the multi-file `wrapperSource` has no `runCrashGuardIfMarked` — the call exists only in `singleWrapperSource` (`src/cli/build/wrapper.ts:76,81`), and for multi-file the check is `src/runtime.ts:40` inside `startApp`, i.e. after the register line, so a guard launch still evaluates the extension (and `config`/`assets`/`runtime` statically, which is the larger exposure).
- The fix belongs in `src/cli/build/wrapper.ts`: guard check above the app-side section, with `config`, `assets`, `startApp` and `extensionRegistry` switched to `await import` like the single-file entry.
