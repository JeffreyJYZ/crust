# `src/plugins/fs*` hunt — 01

Scope: `src/plugins/fs.ts`, `fs-binary.ts`, `fs-scope.ts`, `fs-scope-path.ts`, `fs-scope-store.ts` and
their tests. Read-only source inspection; nothing in `src/` was edited. Five findings, all `measured`
against the real plugin through a scratch tree in `/private/var/folders/.../opencode` (probes called
`createFsPlugin` directly and exited); no GUI app launched, no cursor moved. The theme is the brief's
one: a path string has three different interpretations — `canonical()`'s realpath-based check, the raw
string the command actually runs, and `resolve()`'s lexical fold used to build results — and they
disagree.

## HIGH — every crust app shares one `scope.json`, so a persisted grant widens every other app

- where: `src/plugins/fs-scope.ts:83` — `const file = join(options.root ?? defaultStateRoot(options.app ?? "crust"), SCOPE_FILE);`. `check()` merges persisted paths into the prefixes at `:133-135` via `current()` at `:97-108`.
- what breaks: the doc block at `:14-20` says the store "sits in the app's data directory" and `app` is "usually the config's `app.name`", but the runtime wires the plugin as `createFsPlugin({ allow: fs.scope })` (`src/runtime-plugins.ts:47`) — no `root`, no `app`. So the store is always `defaultStateRoot("crust")/scope.json`, shared by every crust app. Any prefix persisted by one app is loaded as a granted prefix by every other app's `check()`. This is the exact bug the same file already fixed for `store` and `database` (`runtime-plugins.ts:65-69`: "with no adapter it answered `~/Library/Application Support/crust/store.json` for every crust app"), just not for `fs`.
- how reached: a host grants a path with `createFsScope({ allow: [], grants: "page" }).allow({ path })` — the flow `fs-scope-tamper.test.ts:127-131` calls "the way a config or a consent sheet would grant it" — or any host use of the public `createFsScope().allow()`. Prefix persists to the shared file. A *different* app built with its own `fs.scope` then reads that directory: `measured` — App A granted `app-A-private`, App B's plugin configured with only `app-B-scope` read `A-SECRET` from it, and `scopeList` listed both prefixes. Page `scopeAllow` cannot create this itself (refused by default), which is why this is a host-wiring defect rather than a page exploit; the impact is full read/write outside B's configured boundary, not just metadata.
- smallest fix: pass `{ root: appRoot }` (or `app: appId`) at `runtime-plugins.ts:47`, and make `FsScopeOptions` require an explicit root/app so a bare `createFsPlugin()` cannot silently pick the global `"crust"` bucket.

## HIGH — `fs.list` reports the size of an out-of-scope file for an ordinary (non-symlink) entry

- where: `src/plugins/fs.ts:156` (`const full = resolve(dir, entry.name);`), `:161` (`size: … await entrySize(entry, full)`), `:114-124` (`entrySize` guards only `entry.isSymbolicLink()`).
- what breaks: `dir` is the raw path from `scoped()`, so `resolve(dir, name)` folds `..` **lexically** while `readdir(dir)` and `statPath(full)` follow symlinks **through** the OS, and `canonical()` check used a third, realpath-based resolution. When `dir` contains a symlink followed by `..`, the two disagree. `entrySize` calls `scope.check(full)` only when the entry itself is a symlink; a plain file entry reached through a lexically-folded, out-of-scope symlink is never checked, so `statPath(full)` happily returns the out-of-scope target's size. This defeats the exact leak the `entrySize` comment at `:109-113` was written to close.
- how reached: page calls `list` with an in-scope path that passes `check()` (realpath resolves it inside the grant) but folds lexically onto a symlink pointing outside. `measured` tree: `link -> scope/deep/foo`, `scope/xlink -> root/outside`, `list` on `scope/link/../xlink` (realpath → in-scope `scope/deep/xlink`) returned `name: "note.txt", size: 9999` — the size of `root/outside/note.txt` — while the in-scope file's real size was 2. Only `fs.list` read access is needed; `stat` on the out-of-scope file itself is still refused.
- smallest fix: build `full` from the canonical directory (`await canonical(dir)`) rather than `resolve(dir, …)`, or call `scope.check(full)` for every entry, not just symlinks. Canonical directory is the one location all three paths can agree on.

## MEDIUM — `fs.list` reports a phantom path and size 0 for a real file

- where: `src/plugins/fs.ts:156` and `:161` (same lexical `resolve` as above); the returned `path` is `full`, and `size` comes from `statPath(full)`.
- what breaks: with a symlink + `..` directory path, `readdir` lists the OS-resolved directory but `resolve(dir, name)` names a different, usually nonexistent file. The listing therefore publishes a `path` that does not exist and a bogus size, so a page that trusts `ListEntry.path` (documented at `:41` as "Absolute path, so a page never has to join strings") reads the wrong file or gets `not-found` on the next command.
- how reached: `measured`: `link -> scope/deep/real/nested`, `list` on `scope/link/../deep` (OS → `scope/deep/real/deep`) listed real file `x.txt` as `path: scope/deep/x.txt, size: 0`; the file actually lives at `scope/deep/real/deep/x.txt` with 10 bytes. Any in-scope path with a symlink whose target has a different depth than the lexical fold triggers this.
- smallest fix: same as above — derive entry paths from the canonical directory, and use that canonical path consistently for both `path` and `size`.

## MEDIUM — recursive `remove` of a parent directory destroys the scope store despite the store guard

- where: `src/plugins/fs.ts:178-182` (`rm(target, { recursive: recursive === true })` at `:180`); guard at `src/plugins/fs-scope.ts:128-136`, specifically `:131` (`samePath(target, await store())`) — exact-file equality only.
- what breaks: the guard refuses a command whose target *is* `scope.json`, but not one whose target *contains* it. `rm(dir, { recursive: true })` deletes the store along with the directory, and `rename` of the store's parent moves it out of the location the plugin reads. The invariant at `fs-scope.ts:14-20` ("no page command may therefore address it") is violated by containment, and persisted host grants are silently lost on the next launch.
- how reached: the ordinary shape the tamper test itself describes — an app scopes its own data directory and the store lives there. `measured`: host granted `data` via `createFsScope().allow`, `remove({ path: data, recursive: true })` through the scoped plugin succeeded and `data/scope.json` was gone. Impact is integrity/availability (host grants lost, app loses access after restart), not widening.
- smallest fix: in `check`, refuse any target that is the store **or an ancestor of it** (`contains(target, await store())`), and likewise refuse a `rename` destination that would place a directory containing the store elsewhere.

## LOW — `stat`/`remove`/`rename`/`mkdir` return lexical paths that name a different file than the one operated on

- where: `src/plugins/fs.ts:172` (`resolve(target)`), `:181` (`resolve(target)`), `:188` (`resolve(destination)`), `:156` (`resolve(dir, entry.name)`); `src/plugins/fs-binary.ts:96` (`resolve(dir)`).
- what breaks: the check canonicalizes the target (realpath, symlinks, `..`), and the operation runs the raw string, but the reported `path` is a third form: `resolve()`, which folds `..` without following symlinks. Under the same symlink + `..` shape as the findings above, the returned path can point to a different file than the one that was stat'ed/removed/renamed/created — a "path that means different things to different code" in the plugin's own public result.
- how reached: `measured` in the two probes above — `list` returned `scope/deep/x.txt` while the operated file was `scope/deep/real/deep/x.txt`. The same `resolve()` is used by the other four commands, so the same divergence is reachable by passing a symlink + `..` path to `stat`, `remove`, `rename` or `mkdir`.
- smallest fix: return the canonical path from `check()` (have it return the resolved target instead of `void`) and use that single string for the operation and for every reported `path`, eliminating the raw/lexical/canonical split.
