# Hunt 20 — trust boundary: page ↔ app

Field: bridge token issuance/binding, capability label at serve time, origin gate, CSP, content-world
isolation, cross-window reach. Every claim below is `read` (code trace). No GUI, no e2e, no file
edited except this report. I did not run the app, so nothing here is a runtime observation on any
platform.

## HIGH — A page can choose the capability label of a window it creates

- where: `src/plugins/window-create.ts:56-79`; `src/bridge/server/handler.ts:64-93`; `src/bridge/server.ts:49-66`; `src/bridge/client/bootstrap.ts:67-69`
- mechanism: the bridge's only authority input is the label bound to a token when a document is served (`state.labels.set(documentToken, label ?? DEFAULT_WINDOW_LABEL)`), and that label is read from the navigation URL's `?window=` — not from the app's window config. For a **bridge-owned absolute URL**, `appDocument()` deliberately keeps the page-supplied URL byte-exact and appends only the token, so a `?window=` the page put there survives and becomes the new document's authority. The native window label (`parsed.options.label`, used for the duplicate check at `window-create.ts:84`) is unrelated to the authority label. There is no check that the two match.
- reachable by: built app with `security.capabilities` configured so label `worker` holds only `window:create` and label `admin` holds privileged actions. The `worker` page calls `crust.invoke("window","create",{label:"foo", url: location.origin + "/x?window=admin"})`. `isBridgeOrigin` is true → `appDocument()` returns that URL unchanged plus `?token=<process token>`; native tracking uses `"foo"` so the duplicate check does not collide with an open `admin` window; the 302 mints a document token bound to `"admin"`. The new window's page now invokes with `admin`'s grants while being tracked as `foo`. A bridge-owned absolute URL with **no** `window=` is even simpler: it silently binds to `DEFAULT_WINDOW_LABEL` (`main`), which the scaffolds grant `app:invoke` — i.e. every app command (`templates/*/crust.config.ts:13-17`, `src/bridge/server/actions.ts:39-43`).
- smallest fix: make authority equal the native window label. In `appDocument()` for `bridgeOwned` URLs, overwrite/append `?window=` with `parsed.options.label` instead of preserving a page-supplied one, so the duplicate-label check governs the same label the document route binds. Stronger: carry the requested native label into the document route out-of-band and refuse to mint when the URL's label disagrees.

## MEDIUM — Issued tokens are never revoked and the label map grows without bound

- where: `src/bridge/server.ts:54-66`; `src/bridge/server/handler.ts:66,80,153-155`
- mechanism: `state.labels` is only ever written with `.set` (startup process token, then one per served document); no code path deletes an entry. `tokenFromSearch`/`issued` accept any UUID still in the map, so every token ever minted stays a valid bearer for the bridge's whole lifetime.
- reachable by: every full-page load, reload or extensionless client-side route mints a fresh token (`serveDocument`) and leaves the previous one live. A token captured once — from browser history/devtools, a crash dump, or a log line that recorded the navigation URL — keeps working after the page that owned it reloads or closes. A long `crust dev` session with repeated HMR full reloads accumulates one map entry and one live credential per reload.
- smallest fix: evict the previous document token when minting a new one for the same label, and drop entries when a window closes; if exact lifetime tracking is too invasive, at least expire entries by age and cap the map. The test at `server-document.test.ts:20-33` would have to assert that a token from a prior load is rejected after a reload.

## MEDIUM — Every window's event stream receives every other window's events

- where: `src/bridge/server/events.ts:36-60,77-102`; `src/bridge/server/handler.ts:162-163`; emitters `src/plugins/shell-stream.ts:48-55`, `src/plugins/sidecar-control.ts:81-92`, `src/plugins/downloads.ts:61-112`, `src/plugins/deep-link.ts:85`, `src/plugins/network.ts:120`
- mechanism: one `Events` instance holds one `subscribers` Set; `emit()` fans each frame out to **all** connected streams. The event route checks only that the caller holds *some* issued token — it does not pass the caller's bound label to `events.stream`, and `emit` takes no label at all. So a listener in window A sees events produced by commands invoked in window B.
- reachable by: an app with two windows where one runs a shell/sidecar or handles downloads/deep links. A page in the other window calls `crust.listen("shell-output" | "sidecar-stdout" | "download:started" | "deep-link" | "network:request", …)` and receives those payloads (command output text, file paths, incoming URLs) without having invoked the producing command or holding that window's grants.
- smallest fix: thread the token's bound label into `events.stream(port, cors, authority)` and filter frames per subscriber on emit; or require an explicit per-label event allowlist. If app-wide broadcast is intended, document that emitted payloads must never carry data private to one window.

## Checked and clean

- **Token-in-HTML and document-token gating**: `documentResponse` (`server/assets.ts:92-141`) never serialises the token into HTML; the bootstrap reads it from `location.search`, and the document route refuses a request without a token already in the URL (`handler.ts:64-71`). `server-document.test.ts:35-68` asserts a bare `GET /` gets 401 and the HTML contains no token. A local process that merely fetches `/` cannot harvest a credential. `read` plus the named test's assertions.
- **Referrer leak**: `server/http.ts:32-38` sets `referrer-policy: no-referrer` on the document response; `server-document.test.ts:32` asserts it. A token in the URL cannot leave via `Referer` on a top-level navigation. (Lane 05 separately covers the *relative-URL* leak to a foreign base; not re-reported here.)
- **Origin gate**: `server/cors.ts:40-50` accepts own origins and configured dev origins and refuses a present, foreign `Origin`; absent `Origin` is allowed deliberately for WebKitGTK's same-origin `EventSource` (measured by other lanes). CORS headers are only emitted for configured dev origins (`cors.ts:29-38`) and preflight requires one (`cors.ts:52-67`). No bypass found by reading.
- **CSP and inline-script injection**: `server/csp.ts:14-33` gives a per-response nonce on `script-src`, `default-src 'self'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'none'`; `stampInlineScripts` tags authored inline scripts and `jsonForScript` (`client/bootstrap.ts:47-53`) escapes `<`, `>`, U+2028/9 so a `?window=` value cannot close the bootstrap element. The older `</script>` escape is fixed in this tree; not re-reported. An app-supplied `security.csp` replaces the whole policy by design (`assets.ts:138-141`) — a misconfiguration that drops the nonce breaks the page rather than opening a hole.
- **Content-world isolation**: `platform/darwin/content-world-source.ts:21-120` keeps the bearer in an isolated `WKContentWorld`, scrubs `?token=` with `history.replaceState` at document start, and relays only JSON through DOM events; `client/install.ts:146-158` omits `token` from `window.crust` and clears it on `window.__CRUST__` when `crustInvoke` exists. The request/response events (`crust:req`/`crust:res`/`crust:evt`) live on that window's shared `document`, so a forged event affects only scripts in the same page, not another window — no cross-window channel found. `read`.
- **Per-window label as routing hint**: `ctx.window` is consumed only by `window.label` (`src/plugins/window.ts:133`, `src/plugins/window-label.ts`); no handler in this tree uses it to choose a privileged target. A page that lies about `window` in an invoke body can only mislabel `window.label`'s answer; capability authority comes from the token's bound label (`server/invoke.ts:60-68,169-170`). No cross-window "act as" path through the routing hint found. `read`.
- **Dispatcher capability check**: `server/actions.ts:29-43` checks both `app:<name>` and the wire `app:invoke`, so a narrow grant cannot be widened by naming another app command, while the legacy flat grant keeps working. No widening found by reading.
