# Hunt 20 — type-safety holes (lane 18)

## Moderate — Locale JSON values cast to `string` without ever being checked; `translate` then throws
- where: `src/plugins/i18n-load.ts:45` (`catalogue[file.slice(0, -".json".length)] = parsed as MessageTable`), consumed at `src/plugins/i18n-messages.ts:89-90` and `48`.
- mechanism: (read) `loadCatalogue` parses a locale file and checks only that `parsed` is a non-null, non-array object (`i18n-load.ts:39-44`), then casts it to `MessageTable = Record<string, string>` (`i18n-types.ts:10`). The individual values are never checked to be strings. `messageFor` takes `exact = messages[key]` as a `string` and passes it to `interpolate`, which calls `template.replace(PLACEHOLDER, …)` (`i18n-messages.ts:48`). A non-string value makes that call throw `TypeError: template.replace is not a function`. The plugin `translate` handler has no local catch (`i18n.ts:97-117`), so the bridge runner converts it to a `handler-error` ("plugin handler threw …") instead of a clean `bad-request`.
- reachable by: a `crust:i18n.load` command on a directory containing a valid-JSON locale file whose message value is not a string, e.g. `{"greeting": 42}` or `{"greeting": {"text": "hi"}}`. Nothing in `loadCatalogue` rejects it. A later `crust:i18n.translate` for that key throws. This contradicts the loader's own comment (`i18n-load.ts:4-5`) promising a broken catalogue "fails at load time instead of surfacing as a missing translation at runtime" — a non-string value does not fail at load time. A hand-edited locale file reaches it without any attacker; a page that can call `i18n.load` reaches it with an arbitrary directory.
- smallest fix: in `loadCatalogue`, before the cast, assert every own value of `parsed` is a string (`Object.values(parsed).every(v => typeof v === "string")`) and throw the same `CrustError("bad-request", …)` naming the file when one is not; the existing "a document that is not an object is refused" test should gain a case with a non-string value.

## Low — `__proto__.json` locale name is assigned through a plain-object index signature, so the locale silently never loads
- where: `src/plugins/i18n-load.ts:27,45` (`const catalogue: MessageCatalogue = {}`, then `catalogue["__proto__"] = …` when the file is `__proto__.json`).
- mechanism: (read) the catalogue key is the raw filename minus `.json`. A file named `__proto__.json` yields the key `"__proto__"`; on a plain `{}` that assignment invokes `Object.prototype`'s inherited setter and changes `catalogue`'s prototype instead of storing an own property. `Object.keys(catalogue)` (used by `load` for `available` and by `resolveCatalogue`) then never lists that locale, so it can never be selected. This is the exact trap the codebase guards against elsewhere with `Object.create(null)` (`window-persist-store.ts:41-50`, and `Object.defineProperty` in `bridge/client/invoke.ts:56-63`, `bridge/server/bytes.ts:65`) — this loader uses a plain `{}` and no guard.
- reachable by: a locale directory containing a file literally named `__proto__.json` (hand-made or supplied to `i18n.load`). The locale is silently dropped from `available` and unresolvable; no error is raised.
- smallest fix: build the catalogue with `Object.create(null) as MessageCatalogue`, or write entries with `Object.defineProperty(catalogue, locale, { value: parsed, enumerable: true, … })`, matching the pattern already used in `window-persist-store.ts`.

## Checked and clean
- JSON.parse trust boundaries in `src/`: (read) `config/load.ts:75`, `bridge/server/invoke.ts:164`, `single-react.ts:24`, `vite.ts:46`, `packaging/notarize.ts:38,88`, `runtime-crash-store.ts:45,63`, `bridge/client/invoke.ts:107,148` — every one either wraps the parse in `try/catch` and/or follows it with `typeof`/shape guards before reading fields. No unchecked shape used downstream. (The two findings above are the exception: the object-level guard exists but the value-level guard does not.)
- Persisted-store readers: (read) `plugins/store-file.ts`, `plugins/stronghold-file.ts`, `plugins/window-persist-store.ts`, `plugins/fs-scope-store.ts` validate each field (including `Number.isFinite`, base64 length, absolute-path checks) rather than trusting `as Record<string, unknown>`; `__proto__` is handled in the window store.
- Error objects: (read) ~40 caught-value sites all use `error instanceof Error ? error.message : String(error)` (or a `typeof … === "string"` check); no `(error as Error).message` on an unknown caught value. The few `as { code?: string }` casts (`runtime-crash-guard.ts:48`, `plugins/fs.ts:86`, `single-instance-lock.ts:38`, `stronghold-file.ts:126`) only read an optional `code` and compare it to a string, which fails safe when the value is not an object.
- `!` non-null assertions: (read) none in `src` outside tests; the codebase uses `??` fallbacks instead.
- FFI `as unknown as Shim/Library` casts: (read) these declare the symbol table returned by `bun:ffi`'s `dlopen`/`cc`, not a value read from native code. Return widths that matter (`shim_com_init` I64, `shim_apartment_type` I32, HRESULT-vs-int) match their C declarations and are asserted by the `arity.test.ts`/probe tests; no drift found.
- Type predicates (`isStrongholdFile`, `isNotImplemented`, `isCrustInvokeError`, `isExtension`, `isDict`, etc.): (read) each checks the full shape it later relies on; no over-broad guard found.
