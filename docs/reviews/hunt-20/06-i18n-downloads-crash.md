## High — `crash-reporter.configure` accepts a symlinked directory inside the data root, writing crash records outside the fence
- where: `src/plugins/crash-reporter.ts:58-63` (`insideRoot`), `:92-105` (`configure`), `:83-86` (`report`)
- mechanism: `insideRoot` is a purely lexical `resolve()` + prefix test; it never canonicalises. A symlink `<dataRoot>/link -> /tmp/outside` resolves lexically inside the root, so `configure` accepts it. `report` then writes `crashes.log` and `last-crash.json` through the link to `/tmp/outside`. The comment at `:88-91` calls this exact class of write a containment hole, but the check does not implement it.
- reachable by: a page calls `configure({ dir: "<dataRoot>/link" })` where `link` is an existing symlink to a directory outside the data root, then calls `report({ message, stack })`. Measured: `configure` returned `ok: true` and `/tmp/outside/crashes.log` was created containing the report. The sibling-name case is handled; the symlink case is not.
- smallest fix: use the realpath-based containment already written in `src/plugins/downloads-scope.ts` (`canonical()` + `inside()`) in `insideRoot`, and compare the canonical target against the canonical data root.

## Medium — after `configure` repoints the store, signal crashes are written to the data root but `last`/`list` read the new directory, so real crash records are invisible
- where: `src/plugins/crash-reporter.ts:48`, `:69-77`, `:92-105`, `:121-127`; `src/runtime-crash-store.ts:43-72`; `src/runtime-crash-guard.ts:154-159`
- mechanism: `configure` moves the mutable `root` used by `last`, `list` and `report`. `install` deliberately still arms `dataRoot/crash-record.bin` (`:124-126`, asserted by `crash-reporter.test.ts:177`), and the guard writes its parsed records to `dataRoot/crashes.log` and `dataRoot/last-crash.json`. Nothing writes those records into the configured directory. The page's readers therefore look in the wrong place. `clearCrashes(root)` called by the runtime would also target the configured directory and leave the guard's evidence behind.
- reachable by: `configure({ dir: <dataRoot>/reports })` then a real fault. Measured: after writing a signal record into `dataRoot`, `last()` returned `{"crash":null,"root":<dataRoot>/reports}` and `list()` returned `{"crashes":[]}` even though `dataRoot/last-crash.json` existed. The record is not lost on disk, but the API whose job is to surface it reports no crash — a user querying the app sees a clean bill of health after a crash.
- smallest fix: split the roots — keep guard reads (`last`, `list`) and `clearCrashes` pinned to `dataRoot` while `configure` only moves page reports, or make `configure` also repoint the guard target and re-arm. State the choice in the API docs.

## Medium — the 33rd concurrent download is reported as started but never runs (slot exhaustion is a silent lie)
- where: `src/platform/darwin/shim/downloads/00_prelude.c:20,29-30` (`DL_SLOTS 32`), `30_api.c:70,82-88` (`dl_start`), `20_delegate.c:49-60` (`dl_start_done`), `src/platform/darwin/downloads.ts:135-145` (`start`)
- mechanism: `dl_start` only checks the 32 in-flight *starts* (`dl_started_count < DL_SLOTS`) and returns a positive token as soon as the request is sent. The download *slot* is allocated later in `dl_start_done`, which calls `dl_free_slot()` and silently `return`s when all 32 download slots are occupied — no `-setDelegate:`, no retained download, no destination answer, no event. The plugin has already returned `{ok:true}` and created an entry stuck at `"downloading"` with `path: ""` and `progress: 0`.
- reachable by: keep 32 downloads live (slots are freed only on `dl_finished`/`dl_failed` via the JS `dl_forget` call, or on cancel), then start one more. `dl_start` sees `dl_started_count === 0` after the earlier completions, issues a token; the completion finds no free slot and drops the download. Confirmed by reading the C slot lifecycle; not measured here (no WebKit runtime available).
- smallest fix: in `dl_start_done`, when `dl_free_slot()` fails, cancel the download and send a `"failed"` sink event with a reason, or refuse at `dl_start` by also counting occupied download slots so the adapter returns `false` and the page gets the existing `handler-error`.

## Low — `i18n.locale` names a locale the catalogue cannot answer, so the indicator and the text disagree on direction
- where: `src/plugins/i18n.ts:53-55,64-72`; contrast `messages` at `:86-95` and `translate` at `:97-118`
- mechanism: `locale` returns the raw `preferred()` (page choice → override → configured → system) with no catalogue lookup. `translate`/`messages` call `resolveCatalogue` and fall back to another table, reporting the table actually used. When the requested locale is absent, `locale` still reports it. The comment at `:61-62` claims the opposite ("the indicator cannot name one language while the text is in another").
- reachable by: `createI18nPlugin({ messages: { en: { greeting: "Hello" } } })`, then `setLocale("ar")`. Measured: `locale()` returned `{"locale":"ar","dir":"rtl"}` while `translate({key:"greeting"})` returned `{"locale":"en","dir":"ltr","text":"Hello"}`. A page setting `lang`/`dir` from `locale()` lays out an RTL document around LTR English text.
- smallest fix: make `locale` call `resolveCatalogue(catalogue, preferred(), options.locale)` and report `found.locale`, exactly as `messages`/`translate` do.

## Low — `i18n.translate` throws a raw `TypeError` for keys that collide with `Object.prototype`
- where: `src/plugins/i18n-messages.ts:89-90` (`messageFor`), `:43-48` (`interpolate`), `:74-77` (`resolveCatalogue`)
- mechanism: `messages[key]` is an inherited-property read. For `"toString"`, `"valueOf"`, `"constructor"`, `"__proto__"` the lookup returns an inherited function/object, which is `!== undefined`, so `messageFor` treats it as a message and calls `interpolate`, which calls `template.replace(...)` on a non-string. The same pattern at `:74-77` lets an inherited property be mistaken for a locale table. No validation in the command surface (`i18n.ts:101-107`) excludes these keys.
- reachable by: any page calls `translate({ key: "toString" })` on a catalogue that does not define that key. Measured: `messageFor({}, "toString", undefined, "en")` threw `TypeError: template.replace is not a function` (same for `__proto__`, `constructor`, `valueOf`) instead of the intended `bad-request` "key is not in catalogue" error. This is an unhandled exception crossing the bridge rather than a typed refusal.
- smallest fix: require an own property before treating a value as a message or a locale (`Object.hasOwn(messages, key)` and the same for `catalogue[candidate]` and the plural forms at `:96`), falling through to the existing `bad-request` path.

## Wart — three unbounded/one-way collections and one missing event
- where: `src/plugins/downloads.ts:37` (`entries`), `src/platform/darwin/downloads.ts:47` (`reserved`), `src/plugins/i18n.ts:121` (`Object.assign`)
- mechanism: `entries` is never pruned, so every download id, URL and path lives for the whole process. `reserved` is deliberately never pruned (`:42-45`), so every answered path accumulates. `load` only merges via `Object.assign`, so a locale removed from disk is never removed from the live catalogue and `available` keeps listing it. Separately, `cancel` (`:116-137`) sets status to `"cancelled"` but emits no `download:cancelled` event, although the other three terminal-ish states emit; a page that only listens to events never learns the download was cancelled.
- reachable by: long-running process that starts many downloads (both maps grow); calling `load` twice with a locale deleted between calls; issuing `cancel` from a page that listens only to `download:*` events. All read from code; not measured.
- smallest fix: prune settled entries after emitting a terminal event, bound `reserved` (or key it per directory and clear on `setDirectory`), rebuild the catalogue on `load` rather than merging blindly, and emit a `download:cancelled` event from `cancel`.
