# Darwin platform hunt — 07

All claims below are `read` (source inspection) unless marked `measured` (I ran a shell
extraction over the tree). I did not launch a GUI app, run an e2e suite, or move a cursor.
No Windows or Linux runtime claim is made.

## LOW (silent lie) — `PREFLIGHT` does not verify selectors actually sent, so the startup guarantee is false

- where: `src/platform/darwin/preflight.ts:15-154` (the lists) vs the send sites named below; the claim is at `index.ts:3` and `window-adapter.ts:12` ("every selector is preflighted", "fails start() by name").
- mechanism: `startAppKit()` (`appkit.ts:8-16`) checks only the entries in `PREFLIGHT` before `NSApplicationLoad`. Any selector sent from JS via `S.*` but absent from the lists is guarded only at send time (`objc.ts:95-97` `must()`), and any selector sent from C is guarded not at all. The promise that a missing selector names itself at `start()` therefore holds only for the curated subset.
- reachable by: `measured` — I extracted every `S.<x>(r, "<sel>"…)` from non-test TS and every `sel_registerName("<sel>")` from all `.c` files and diffed against `preflight.ts`:
  - TS sends missing from `PREFLIGHT`: `setTitlebarAppearsTransparent:` (`window-create.ts:116`, sent on every vibrancy window), and `configuration`/`userContentController`/`userScripts` (`content-world.ts:35-37`, sent on every window with a token URL). These are guarded at send; a system lacking one fails mid window-create (or, for the three content-world reads, silently takes the fetch fallback via the `catch` at `content-world.ts:39-42`) instead of at startup.
  - C sends missing from `PREFLIGHT` and with no `class_getInstanceMethod`/`respondsToSelector` guard at the call site: the whole `shim_window_set_material` chain (`shim/115_window_material.c:14-42`: `contentView`, `bounds`, `alloc`, `initWithFrame:`, `setAutoresizingMask:`, `setBlendingMode:`, `setState:`, `setMaterial:`, `addSubview:positioned:relativeTo:`, `setOpaque:`, `clearColor`, `setBackgroundColor:`), `shim_app_set_icon` (`shim/50_app.c:17-35`: `initWithContentsOfFile:`, `setApplicationIconImage:`), and `shim_webview_new`'s `initWithFrame:configuration:` (`shim/30_webview.c:31-32`). A macOS build missing one of these raises an uncaught Objective-C exception → SIGABRT with no JS error, exactly the failure PREFLIGHT exists to replace.
  - `measured` scale: C sends roughly 180 distinct selectors; `PREFLIGHT` names about 40. The C units that self-check (notifications via `nf_has_instance`, panel via `panel_has_instance`, `shim_window_is_visible` etc. via `class_getInstanceMethod`) are the exception, not the rule.
- smallest fix: add the four TS selectors to `instanceSelectors` in `preflight.ts`; for C-only selectors either add them to `internalInstanceSelectors`/`internalClassSelectors` where the owning class is stable, or give each C send the same `class_getInstanceMethod` null-check the liveness helpers use. Soften the "every selector" comments until the two sets match.

## LOW (silent lie) — `nativeWindow(label)` hands out a pointer to a closed window; its callers are the window adapter

- where: `windows.ts:82-85` (`native`), `window-store.ts:36-39` (`native` passthrough), `platform.ts:142-145`, `window-adapter.ts:15-24` (`require`) and `:70-95`.
- mechanism: unlike `handle()`/`webview()`/`labels()`, `native()` does no `#isOpen` check and no prune. After `window.close(label)` sends `-close` but leaves the entry in the map, `native(label)` still returns the `NSWindow *`. That object is deliberately kept alive by `setReleasedWhenClosed:0` (`window-create.ts:63`), so sends to it are memory-safe but act on a window no longer on screen; `setTitle` even passes its own readback (`window-adapter.ts:88-94`) because the dead object still answers.
- reachable by: `window.create("x")` → `window.close("x")` (adapter `close`, no prune) → `window.setTitle("x", "new")` / `window.focus("x")` → `require("x")` returns the stale pointer, the command reports success, nothing changes on screen. `isOpen("x")` on the same label correctly reports false, so two commands disagree. This is *not* a crash and the closed-but-tracked state is intentional (`src/plugins/window-closed-label.test.ts:32-58`), but the commands' success is misleading.
- smallest fix: have `require()` go through a liveness-checked accessor (or call `platform.window(label)` first) so geometry/chrome/title commands on a closed label throw `unknown-window` the way `isOpen` reports `open:false`.

## LOW (resource leak) — `+1` Cocoa objects never released in the shim's one-shot/persistent paths

- where: `shim/50_app.c:17-35`, `shim/40_window.c:25-36`, `shim/115_window_material.c:19-42`, `shim/121_content_world.c:16-24`, `:54-74`.
- mechanism: each of these builds an object with `alloc` + an `init…` that returns `+1`, uses it, and never sends `release`. The download unit documents the rule explicitly (`shim/downloads/00_prelude.c:67-73`) but the main shim does not follow it. `NSVisualEffectView` is retained by `addSubview:` so the view itself is owned, but the extra `alloc` reference leaks; `NSString` title/source/name objects and the `WKUserScript` leak outright.
- reachable by: every `app.icon` apply (once at startup), every `shim_window_set_title`/`setTitle` call, every material window, and every `installContentWorldBridge` call (two scripts + the isolated world name). Bounded by call count, so a page calling `window.setTitle` in a loop grows memory without bound.
- smallest fix: release the `+1` object after the consuming send in each helper (`shim_window_set_title` after `setTitle:`, `shim_webview_add_user_script` after `addUserScript:`, `shim_app_set_icon` after `setApplicationIconImage:`), as `dl_file_url`/`dl_start` already do.

## LOW (race / lost tracking) — downloads: cancel before the completion fires is refused, and a 33rd live download goes untracked

- where: `shim/downloads/30_api.c:67-88` (`dl_start`), `:91-101` (`dl_cancel`), `shim/downloads/20_delegate.c:49-61` (`dl_start_done`).
- mechanism: `dl_start` mints and returns a token immediately but the `dl_downloads[slot]` entry that `dl_slot(token)` needs is only written later, in the async `startDownloadUsingRequest:completionHandler:` block. `dl_cancel` calls `dl_slot(token)` and returns 0 when the slot is not yet filled, so it refuses the cancel. Separately, `dl_start_done` decrements `dl_started_count` and frees the block slot *before* calling `dl_free_slot()`; if all 32 download slots are live it returns without storing the download or setting its delegate, so WebKit downloads it with no delegate and JS gets no events, no progress and no cancel. `dl_start` gates on `dl_started_count >= 32`, not on live slots, so a 33rd start is admitted while all 32 slots are occupied.
- reachable by: `downloads.start(url)` then `downloads.cancel(id)` in the same tick (the common "user changes mind" path) → cancel returns false and the file still downloads. For the slot bug: start 32 downloads and let them all reach their delegate (slots full, `dl_started_count` back to 0), then start a 33rd → its completion finds no free slot and the transfer is invisible to the adapter (`downloads.ts:135-157`).
- smallest fix: keep a token→slot intent record at `dl_start` time (or queue cancels until the slot fills), and gate `dl_start` on a free *download* slot rather than `dl_started_count`; in `dl_start_done`, refuse to consume the block slot if no download slot is available.

## Checked and clean

- **Objective-C send arity and width** — `read`: every `S.*` wrapper in `objc.ts:100-151` maps to a `shim_send_*` in `shim/20_sends.c` whose `objc_msgSend` cast has the matching parameter count and scalar width (BOOL returned as `char` at `:25-31`, `long long` returns at `:33-39`, nil `id sender` passed explicitly for the colon toggles in `shim/92_window_state.c:55-86`). `arity.test.ts` walks all C and binding sources; I confirmed its declarations in `index.ts:49-168` agree with the C prototypes for the window/constraint/webview sends. No drift found.
- **Objects crossing `bun:ffi`** — `read`: no C export returns an `NSString`/`NSNumber`/tagged pointer. String reads copy into a C buffer (`shim_window_title_utf8` returns `-UTF8String` consumed synchronously as `cstring`; `crust_os_locale`, `crust_os_app_version` copy into `static char[]`; panel/download path reads copy immediately). The tagged-pointer rule in `shim/10_prelude.c:2` is respected at every boundary I traced.
- **Window registry after `-close`** — `read`: `setReleasedWhenClosed:0` (`window-create.ts:63`) keeps the object addressable; liveness is the measured `inAppWindows`-gated rule (`liveness.ts:21-25`, `windows.ts:117-143`), not `-windowNumber`. `handle()`, `webview()` and `labels()` all prune/filter closed entries consistently; `number()` returns 0 for a closed window. The only rough edge is the `native()` accessor reported above, not a use-after-free.
- **Run-loop reentrancy** — `read`: the pump is a non-rearming `setTimeout` chain (`platform.ts:64-79`) calling `shim_pump`, which drains one event per tick (`shim/50_app.c:84-105`); sheets are awaited by a `setTimeout` poll (`sheet.ts:28-31`) and `shim_open_panel` refuses a second request while one is up (`shim/75_open_panel.c:6`). `quit()` stops the pump before closing windows and calling `-terminate:` (`platform.ts:166-185`), so a re-entrant close cannot interleave with a pump tick.
- **`JSCallback` lifetime** — `read`: the trampolines in `find.ts:29-56`, `menu-api.ts:66-91`, `status-bar-item.ts:45-66` and `downloads.ts:97-124` are held in module- or closure-level variables, so C's stored function pointer cannot outlive a collected callback. Each C unit registers exactly one IMP/trampoline as its comments require.
