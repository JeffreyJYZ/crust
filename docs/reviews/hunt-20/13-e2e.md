# E2E harness and probes — defect hunt

All claims below are `read` (source inspection). Nothing was built, launched or run; no suite, GUI app or cursor was touched, per the brief.

## MEDIUM — Deadline timeout keeps the killed child's exit code, so `exit 0` can PASS on a harness kill
- where: `scripts/harness/probe.ts:137-147` (timeout branch) and `:156-166` (return); compare `scripts/harness/run.ts:109-116`, which nulls it. Affected callers: `scripts/e2e.ts:132`, `scripts/e2e-dev.ts:86`, `scripts/e2e-native.ts:128`, `scripts/dev-binary/run.ts:40`.
- mechanism: `probe()` never resets `code` when `outcome === "timeout"`. The deadline sends SIGTERM to the process group; the app's registered handler exits 0 (`src/runtime-process.ts:16`, `process.exit(0)`), so `exited` settles with status 0 and `probe` returns `{ code: 0, timedOut: true, ended: "timeout" }`. Callers that assert only `run.code === 0` then print a PASS "exit 0" for an app the harness killed. The overall verdict still fails on the missing proving-line assertion, but the detail line lies — the exact class `scripts/e2e-detail.test.ts` exists to prevent.
- reachable by: a page/bridge hang so the proving line never arrives; the 15–45 s deadline fires, SIGTERM is handled cleanly, code 0 is captured. Suites that DO guard (`scripts/e2e-notes.ts:104`, `scripts/single/phases/build.ts:81`, `scripts/window/checks/finish.ts:25`) are unaffected — the defect is the inconsistency.
- smallest fix: in `probe()`'s timeout branch set `code = null` before returning, exactly as `runCommand()` does; then every caller is safe without editing each suite.

## MEDIUM — Normal-path focus restore bypasses the guard's refusal, re-activating a leftover test app
- where: `scripts/e2e.ts:157-160,172`; same pattern in `e2e-single.ts:33-36,55`, `e2e-window.ts:29-32,43`, `e2e-dev.ts:113-116,128`, `e2e-notes.ts:42-45,64`, `e2e-native.ts:155-158,169`, `e2e-dev-react.ts:34-37,56`, `e2e-dev-binary.ts:40-43,175`, `e2e-capability.ts:27-30,101`, `probe-tray.ts:18-21,142`.
- mechanism: each suite captures `frontmost` with raw `captureFrontmost()` and restores that raw name in `finally`. `guardFocus()` separately captures and *decides* a target, refusing own test apps, scratch-path apps and windowless apps (`scripts/harness/guard.ts:92-101,156-173`). On a normal return the `finally` wins and activates whatever was raw-captured, defeating the refusal the guard exists to enforce.
- reachable by: two e2e runs back to back, or a run after an aborted one, leave a crust test app frontmost; the next suite raw-captures it and re-activates it at the end instead of the fallback Ghostty — the cascade `guard.ts:3` says the refusal turns into "one leak".
- smallest fix: use the value `guardFocus()` already returns (the decided target) for `restoreFocus` too; drop the second raw `captureFrontmost()` call.

## MEDIUM — `e2e-notify` cleanup aborts before removing scratch and restoring focus
- where: `scripts/e2e-notify.ts:154-159`.
- mechanism: unlike every other suite, neither `clearSurvivors(builtBinary)` nor `rm(root, …)` is wrapped in `.catch(() => undefined)`. A throw in either skips `restoreFocus(frontmost)` and leaves the scratch tree behind; the outer catch only prints FAIL.
- reachable by: the notification app spawns WebKit helpers whose argv differs from `builtBinary`, so the path-kill in `clearSurvivors` leaves them holding files under `root`; `rm(root, { recursive, force: true })` can then fail with a busy/locked file, and focus is never returned. A `Bun.spawn("pgrep")` failure inside `clearSurvivors` has the same effect.
- smallest fix: wrap each of the two cleanup calls in `.catch(() => undefined)`, matching `e2e-single.ts:51-55` and `e2e-window.ts:40-43`.

## LOW — Truncated page-answer line throws in `pageLines()` and reports no window checks
- where: `scripts/window/answers.ts:20-25`, called at `scripts/window/proof.ts:104`.
- mechanism: the regex accepts any line containing a balanced `{...}` and `JSON.parse(json)` is unguarded. The file's own comment claims "A truncated answer is still counted; only its fields are missing" — false. A malformed fragment throws, propagates past `proof()` to `e2e-window.ts`'s outer catch, and none of the `WINDOW_CHECKS` are emitted; the run reports one generic FAIL.
- reachable by: the window probe matches `WAIT_FOR_EXIT = /(?!)/` (`scripts/window/expectations.ts:143`), so it always waits for natural exit or the 40 s deadline; a SIGKILL from that deadline landing mid `console.log` of a page answer can leave a truncated `{...}` fragment in stdout, which is where JSON.parse throws.
- smallest fix: catch `JSON.parse` failures and keep the line with empty fields, so the exact tag-count assertion (`proof.ts:120-136`) reports the missing/malformed answer instead of crashing.

## LOW — Survivor assertion on a shared `crust-single-` prefix false-fails a concurrent lane
- where: `scripts/e2e-dev-binary.ts:110,159,161-162`.
- mechanism: `RUNNER = join(tmpdir(), "crust-single-")` is fed to `survivorsOf()` via `pgrep -f`, which matches any single-file dev runner on the machine. The comment at line 159 admits "another lane could own one" yet the assertion still requires zero matches.
- reachable by: any other `crust dev <single file>` (another agent or another suite) alive during this suite's survivor check → non-empty survivors → false FAIL unrelated to this run.
- smallest fix: capture this run's exact runner directory/pid and check only that, or drop RUNNER from the assertion.

## LOW — Raw absolute paths with regex metacharacters passed to `pgrep -f` in survivor checks
- where: `scripts/e2e.ts:60,143`, `scripts/e2e-notes.ts:53,115`, `scripts/single/phases/build.ts:91`, `scripts/window/proof.ts:96,153`, `scripts/dev-binary/run.ts` callers `e2e-dev-binary.ts:111,162`. Contrast `scripts/e2e-native.ts:40-44`, which runs every pattern through `pgrepLiteral()` with a documented reason.
- mechanism: `pgrep -f` treats the path as a regex; `.` in `.app` and other metacharacters over-match, so an unrelated process can be counted as a survivor and fail the run. This can only cause false FAILs (the exact path always matches its own regex), never a false pass.
- reachable by: any concurrent process whose argv happens to match the loosened pattern, e.g. another checkout under a similar path.
- smallest fix: route every survivor pattern through `pgrepLiteral()` as `e2e-native.ts` does.

## Checked and clean
- **Deadline coverage**: `harness/run.ts`, `harness/probe.ts`, `lib/live-run.ts` all bound children with a hard deadline plus SIGTERM→SIGKILL escalation; `live-run.wait()` (`live-run.ts:93-108`) returns null on both child exit and deadline, and `harness/wait.ts` has a real deadline. No unbounded `await child.exited` outside `e2e-notify.ts` (covered above).
- **Process-group cleanup**: `runCommand`, `probe` and `spawnLive` all spawn `detached` and signal the negative pid, so runtime/webview children are included; `survivorsOf`/`survivorsOfPids` are bounded by a settle deadline. `dev.ts:45-65` and `watch.ts:131-148` capture child pids before stopping, avoiding the `pgrep -f vite` false pass.
- **Scratch cleanup**: every scratch-using suite removes its temp tree in `finally` (except notify, above); `e2e-window.ts:46-49` re-checks `scratch gone` after the swallow-caught `rm`, so a failed removal is reported rather than hidden.
- **Window observations**: `window/proof.ts:120-136` checks the answer tags exactly in both directions (missing, extra, repeated), so a page that never ran or loaded twice cannot pass on an exit alone; check groups assert fields of page-reported answers, not the plugin's `ok` alone. `focus` (`windows.ts:87-107`) is the documented exception — the page cannot see which window is key, so it asserts answer consistency; that is a stated limitation, not an unflagged defect.
- **Focus guard mechanics**: `guard.ts` restores idempotently from `exit` and three signals with a blocking runner, refuses own/windowless/scratch apps, and timeboxes every osascript at 3 s — sound; the defect is the caller wiring above, not the guard itself.
