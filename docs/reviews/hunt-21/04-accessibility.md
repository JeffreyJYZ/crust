# Hunt 21 — lane 04: accessibility and activation

All claims below are `read` unless stated otherwise. No GUI, e2e, or native call was made.

## MEDIUM — An AXChildren refusal is reported as "AX listed no windows"
- where: `src/platform/darwin/shim/106_accessibility.c:114-133`, `src/platform/darwin/accessibility.ts:85-89`, `src/plugins/accessibility-trust.ts:103-111`
- mechanism: `crust_ax_element_count` initializes `count = -1` and only assigns a real count on the AXChildren success path. When `AXUIElementCopyAttributeValue(window, AXChildren, …)` fails (or returns a null children array) the code sets the correct reason string but still returns `-1`, which the TS adapter maps to `AX_STATUS.noWindowsListed`. The plugin then answers `not-implemented` with `requires: "AXUIElementCopyAttributeValue (AXWindows)"` and a message that begins "0 elements, because AX listed no windows for this process … not evidence that the window is missing". That is the opposite of what happened: AX **did** list windows, and the child walk was what got refused. `AX_STATUS.refused` (`-2`) is only produced by `AXUIElementCreateApplication` failing or the AXWindows read failing, so this branch can never be reported as a refusal of AXChildren.
- reachable by: any app whose first AX window does not answer AXChildren — e.g. the first entry in `AXWindows` is a panel/status window that lacks the attribute (AXErrorAttributeUnsupported -25205), or an untrusted process where the child read is refused (AXErrorAPIDisabled -25211). AXWindows succeeded, so `window_count > 0`; the child call fails; `count` stays `-1`. The caller of `accessibility.elementCount` is told the window list was empty and that AXWindows is the call to fix.
- smallest fix: return `-2` on the `child_status != AX_OK || !children` branch (only the `window_count <= 0` branch should yield `-1`), and carry the failing attribute in `requires` so the message names AXChildren.

## MEDIUM — `trusted` and `elementCount` reject the invoke instead of answering a typed refusal
- where: `src/plugins/accessibility-trust.ts:55-58` (`trusted`) and `:85-101` (`elementCount`); contract at `:6` of the same file
- mechanism: the file promises "Every refusal is a typed value, never a throw", and `prompt`, `announce`, `title` and `focus` all wrap their adapter call in `try/catch` and return `{ ok: false, code: "handler-error" }`. `trusted` and `elementCount` do not. Any exception from `adapter.trusted()` or `adapter.elementCount()` propagates out of the command handler as a rejected promise rather than the typed failure shape the other four commands guarantee. `createAccessibilityPlugin(adapter)` is an exported public extension point (`accessibility.ts:88`) and `AccessibilityAdapter` is a structural interface, so an app that supplies its own adapter is a first-class caller.
- reachable by: an app registers `createAccessibilityPlugin(myAdapter)` where `myAdapter.trusted()` or `.elementCount()` throws (its native bridge unavailable, a decode error, or any adapter-level fault). `crust:accessibility.trusted` / `.elementCount` then rejects the invoke; a page awaiting the result sees an exception instead of `{ ok: false, code: "handler-error", message }`. The darwin adapter has the same hole on the FFI path: `report()` → `reasonOf()` calls `unit.symbols.crust_ax_reason()` with no guard.
- smallest fix: wrap both adapter calls in the same `try/catch` used by `prompt`, returning the `PromptFailure`-shaped `{ ok: false, code: "handler-error", message }`.

## MEDIUM — The page a11y tree omits shadow DOM and falsely refuses focus inside it
- where: `src/bridge/client/a11y-page.ts:138-145` (`walk` over `el.children`) and `:171-180` (`activeElement !== el` check); doc claim at `docs/agents/a11y-page-tree.md:5-6`
- mechanism: `pageTree` walks only `el.children`, which never crosses a shadow root, so every shadow-DOM subtree is absent from the reported tree while the result still says `ok: true` with no caveat. `focusElement` calls `.focus()` on the matched element correctly, but `Document.activeElement` returns the shadow **host** for a node inside a shadow root, so `active !== el` is true and the command answers `not-focusable` for an element that did take focus. The doc describes the API as "the page's own view of its DOM" and promises that checking `activeElement` proves focus landed; neither holds for web components.
- reachable by: any page using a custom element with a shadow root (a common component pattern). `crust.a11y.pageTree()` returns nodes with no entry for the shadow content; `crust.a11y.focusElement('#host button')` on a focusable internal button returns `{ ok: false, code: "not-focusable" }` even though focus moved. The fake DOM in `a11y-page.test.ts` has no shadow-root case, so the suite cannot catch either behaviour.
- smallest fix: in `walk`, recurse into `el.shadowRoot` when present; in `focusElement`, check the active element through each ancestor's `shadowRoot.activeElement` chain (or accept the host when the focused node is inside it) before reporting `not-focusable`. Add a test double whose `focus()` sets a shadow host's `activeElement`.

## LOW — `focus` never returns `bad-request` for an unknown label; the documented branch is dead
- where: `src/plugins/accessibility-page.ts:147-154`
- mechanism: the catch reclassifies an error as `bad-request` only when `error.name === "CrustError"`. No adapter in the tree throws a `CrustError`: `darwinAccessibilityAdapter().focus` (`src/platform/darwin/accessibility.ts:142-152`) returns `{ focused: false, reason: "no AX window matched …" }`, which the handler relays as `{ ok: true, focused: false }`. The comment "An unknown label is the caller's own mistake, so it stays bad-request" therefore never holds for the real adapter.
- reachable by: `crust:accessibility.focus({ label: "does-not-exist" })` on macOS. The caller gets a successful answer with `focused: false` rather than the `bad-request` the code comment and the `AccessibilityFailure.code` union advertise.
- smallest fix: either drop the dead branch and document the `ok: true, focused: false` shape, or have the handler return `bad-request` when the report says no window matched.

## Checked and clean
- **`requires` gating and platform naming** — `read`: `accessibilityNeed` (`accessibility-requires.ts:100-118`) covers all six commands on darwin/linux/win32 and falls back to a generic adapter requirement for unknown platforms. Every `missing()`/`unsupported()` path in `accessibility.ts:109-126` passes `need.requires` through, and the Linux/Windows refusals name `gtk_widget_announce` / `EVENT_OBJECT_LIVEREGIONCHANGED` as promised by `a11y-announce.md`. `hasAnnouncement` is only a query; it is not used as a hidden gate. `arity.test.ts:98-172` walks every `.c` file and every binding module in the darwin shim dir, so the `crust_ax_*` declarations are checked for arity (the doc line "all pointer+int" is imprecise for `crust_ax_title`, which is pointer+pointer, but the guard itself is real).
- **Trust probe never prompts** — `read`: `crust_ax_trusted` calls only `AXIsProcessTrusted()` (`106_accessibility.c:69-73`); the prompt option dictionary and `AXIsProcessTrustedWithOptions` are confined to `crust_ax_prompt` (`:77-91`), and only the `prompt` command reaches it. No test in `accessibility*.test.ts` invokes a real dialog (`accessibility.test.ts:1-5, 174-186`).
- **Announce priority and post** — `read`: `priorityOf` maps only `"assertive"` to assertive and everything else to polite (`accessibility-types.ts:11-13`); the C unit translates those to `NSAccessibilityPriorityHigh` 90 / Medium 50 and builds the `{ AXAnnouncement, AXPriority }` dictionary with constant strings (`106_accessibility_page.c:108-134`). Both strings stay native-side, so no tagged-pointer `NSString` crosses `bun:ffi` (`a11y-announce.md:8`).
- **Activation policy wiring** — `read`: `app-loop.ts:45,50,53,92-97` sets `testing.activation` before the platform exists, installs `raiseAppOnce` as the one raise, and forces `activate: "never"` for both probe modes via `launchActivateMode` (`activation-policy.ts:48-50`). `activationRefused()` gates only `"none"`; `demandActivation()` raises at most once and is a documented no-op without a raise or under `auto` (`:61-65`, test `activation-policy.test.ts:60-63`). `testing.activation` is an enum validated before it reaches this state (`config/validate-testing.ts:19-25`), so an arbitrary mode cannot silently skip activation.
- **Announce ordering** — `read`: each `announce` handler posts synchronously through `announce(text, priority)` and only then reads `trusted`; two concurrent calls cannot reorder the posts because the FFI call is synchronous. No global pending slot or queue exists in this path (contrast the testing-namespace lane).
- **No cross-process tree claim** — `read`: the AX walk is built from `getpid()` (`106_accessibility.c:100-101`), and the empty-list refusal explicitly says it is not evidence a window is missing (`accessibility-trust.ts:104-110`); the page-side tree carries the DOM-not-OS note (`a11y-page.ts:26-28`). Neither claims screen-reader reachability.
