# Hunt 21 — CI and gate scripts, as false-pass risk

Claims are labelled `measured` (I ran it) or `read` (source inspection). No build, e2e suite,
GUI app or cursor was touched. The two `bun test` invocations were short foreground runs of the
repo's own test script; the JUnit report they wrote to `/tmp` was inspected and no repo file was
changed (tree is clean apart from this report). Prior round's `12-release-ci.md` / `13-e2e.md`
findings are not re-reported here; the probe/guard test-gap below is a *new* consequence of their fixes.

## HIGH — `bun run test` silently omits the two regression suites for the previous round's false-pass fixes

- where: `package.json:31`, `scripts/harness/probe.test.ts:1-47`, `scripts/harness/guard.test.ts:1-187`
- mechanism: the `test` script lists `./src ./examples scripts/skill scripts/release scripts/windows` and then *names individual files* under `scripts/harness/` — `focus-enforce.test.ts` and `focus.test.ts` — but never names `guard.test.ts` or `probe.test.ts`. Neither is in a directory the script scans. `bun run test` therefore reports a full green suite (2,675 pass / 417 files, `measured`) while 12 tests in those two files never execute. `probe.test.ts` is the exact regression for hunt-20's HIGH "a killed app prints exit 0": it asserts `result.code === null` after a deadline SIGTERM. `guard.test.ts` is the focus-guard suite added by the companion fix.
- reachable by: any ordinary `bun run test` locally, `ci.yml:60`, and `scripts/release/gate.ts:17-19` (the release gate also calls `bun run test`). A regression that reintroduces `code: 0` on a harness timeout — the class that made an e2e print PASS for an app the harness had killed — would pass the whole gate. The test that would catch it is not run. All three entry points are green without it.
- smallest fix: replace the two explicit harness filenames with the directory `scripts/harness` (or add both filenames), in both `test` and `test:no-skips`; add an assertion that the expected harness suites appear in the JUnit report so an omission fails rather than under-counts.
- evidence: `measured` — JUnit from the exact `bun run test` command lists only `scripts/harness/focus-enforce.test.ts` and `scripts/harness/focus.test.ts` under harness; zero suites from `probe.test.ts`. Running `bun test scripts/harness/probe.test.ts scripts/harness/guard.test.ts` directly: 12 pass, 0 fail. `read` — `package.json:31`, git shows `probe.test.ts` added in `9d40ec8` and `guard.test.ts` in `fad507e`, neither ever added to the script (no commit touches `package.json` for them).

## MEDIUM — `check:lines` skips a real source tree because `SKIP` contains `build`

- where: `scripts/line-cap.ts:14` (`SKIP` set), `:29` (`if (SKIP.has(entry)) continue`), `src/cli/build/**`
- mechanism: `walk()` prunes *any* directory named `build`, at any depth. `src/cli/build/` is not generated output — it holds 12 shipped source/test files (`wrapper.ts`, `stages.ts`, `assets.ts`, `wrapper.test.ts` at 180 lines, etc.) and is inside a root the cap claims to cover. The cap therefore cannot fail on that tree. `scripts/release/line-cap-roots.test.ts:13-22` was written to stop exactly this class of blind spot but only asserts that `ROOTS` contains each name; it never checks that `SKIP` does not shadow a real subtree.
- reachable by: a file in `src/cli/build/` grows past 200 lines — `check:lines` still prints "PASS no file exceeds 200 lines under src, scripts, examples, site, templates" and `ci.yml:65` stays green. `measured`: a 250-line `src/cli/build/.linecap-probe.ts` PASSED; the identical file at `src/.linecap-probe.ts` FAILED with its line count. Both probe files were removed.
- smallest fix: scope the build-output skip to the paths that are actually generated (`dist`, `.next`, `node_modules`, `target`, `.git`, `web`) and either drop `build` or key it on a relative path rather than a bare directory name; add a unit test that a >200-line file under `src/cli/build` is reported.
- note: `measured` — `check:lines` PASS on the tree as shipped; the 250-line probe proved the exclusion. `read` — the `SKIP` set and the roots test.

## MEDIUM — `check:links` ignores the navigation that every docs page renders

- where: `scripts/check-links.ts:29-37,42-50`, `site/lib/nav.ts`, `site/lib/search.ts:11-13`, `site/components/sidebar.tsx:34`, `site/components/palette.tsx:98`
- mechanism: `pages()` reads only files named `page.mdx` under `site/app`, and `LINK` matches only `](/…)` and `href="…"`. The sidebar and the command palette are built from `site/lib/nav.ts` entries shaped `href: "/…"`, which `LINK` does not match and which live outside `site/app`. So `check:links` can print "PASS N routes, every internal link resolves" while a nav entry points at a page that does not exist. The script's own stated reason for existing — "a renamed page leaves a 404 nobody clicks until a reader does" — is precisely the case it misses, and in the nav that is the primary way a reader navigates.
- reachable by: rename or delete a guide page without updating `nav.ts` (a routine docs edit). `measured`: changing the `Clipboard` nav entry to `/docs/guides/clipboard-DEAD` left `bun run check:links` at PASS "63 routes, every internal link resolves"; the file was restored byte-for-byte. The gate would not catch the 404 in the sidebar or the palette.
- smallest fix: also read `site/lib/nav.ts` (or import `NAV`) and assert each `href` is in `known`; better, derive the routes and nav from one source so the comparison is structural, not regex-based.
- note: `read` — route/nav wiring; `measured` — the injected dead href passing the gate.

## LOW — `skill:check` is the only guard for the committed `SKILL.md` table and is not in CI or the release gate

- where: `package.json:45`, `scripts/skill.ts:83-90`, `.github/workflows/ci.yml:58-85`, `scripts/release/gate.ts:11-31`
- mechanism: `scripts/skill.ts --check` is the only code that compares the committed `site/public/SKILL.md` command table to the live registry and fails on staleness or bad frontmatter. No workflow and no gate script calls it. `bun run test` runs `scripts/skill/render.test.ts`, which checks `render()` output and pins the namespace count at 34, but never compares the rendered table to the file on disk; `frontmatter.test.ts` tests the parser, not the shipped file. The `format:check` script is likewise absent from CI.
- reachable by: a contributor adds a namespace/command and runs `bun run test` (green) but not `bun run skill`; the committed skill ships a stale command table. The skills CLI installs it without complaint because frontmatter is intact — only the command list is wrong. `measured`: the committed table is current today (`skill:check` PASS), so this is a gate-coverage gap, not a present defect.
- smallest fix: add `bun run skill:check` to the macOS gate next to `check:links`/`check:parity`.
- note: `read` for the wiring; `measured` for the current PASS.
