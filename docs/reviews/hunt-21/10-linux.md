# Hunt 21 — Linux platform layer (`src/platform/linux/**`)

Every claim below is `read` (source read on macOS; no GTK/GLib/WebKit runtime on this machine). No
Linux runtime observation is claimed. All paths are reachable by page commands unless stated.

## Crash — the snapshot buffer is global, so a late callback from one capture can be read by another

- where: `src/platform/linux/shim/90_snapshot.c:30-38` (the one `shot_*` result set), `:122-155` (`shim_snapshot_done`, no generation check), `:159-172` (`shim_snapshot_take`); `src/platform/linux/snapshot.ts:97-144` (`inFlight`)
- mechanism: `shim_snapshot_take` resets the single `shot_state/shot_len/shot_error` and calls WebKit's async `get_snapshot`. `inFlight` in TS only stops a *second JS call while the first promise is pending*. It is cleared in `finally` on the 5000 ms timeout, and on every completion, while the C callback can still arrive afterwards. When a late callback finally runs it writes into the same `shot_bytes` and sets `shot_state = 1` — the state the *next* capture polls for. That capture then reads the earlier view's picture with the earlier width/height/scale. There is no request id in C or JS to tell which result belongs to which take. `shot_bytes` is also reused in place (`:104-115`) with `shot_len` reset to 0 at callback entry (`:128`), so the bytes can be overwritten mid-read of a slow consumer.
- reachable by: page calls `window.capture` on a heavy page; WebKit answers after the 5000 ms deadline so the promise rejects and `inFlight` is false. Page calls `window.capture` again (possibly on a different window). WebKit's first callback lands during the second capture's poll loop and answers it with the first view's PNG. On a machine where two captures overlap without a timeout (two windows, two invokes in one tick), the JS guard refuses the second by name, so the timeout path is the concrete way in.
- smallest fix: add a monotonically increasing generation counter in C; have `shim_snapshot_take` return/record it, pass it as `user_data` to the callback, and ignore a callback whose id is no longer current. Mirror the id in `takeLinuxSnapshot` so a result from a timed-out take cannot satisfy a later one; reset `shot_cap`/free `shot_bytes` only when no callback can still write.

## Wrong answer — the tray menu flattens labels on `\n`, so one item becomes two rows and clicks land on the wrong handler

- where: `src/platform/linux/shim/81_tray.c:101-137` (`shim_tray_menu` joins labels with `\n` then splits on `\n`), `:71-75` (`shim_tray_on_item` uses `(int)(long long)data - 1`); `src/platform/linux/tray-adapter.ts:84-99` (`joined = next.map(...).join("\n")`), `:121-133` (`items[index]`); `src/plugins/tray-args.ts:43-63` (only checks non-empty string)
- mechanism: the C side uses `\n` as the row delimiter, but a page-supplied label may itself contain `\n` (or a `\n` inside a label is indistinguishable from the sep). With `items = [{label:"a\nb", onClick:A},{label:"c", onClick:C}]` the wire is `a\nb\nc`; C builds three menu rows `a`, `b`, `c` and connects their `activate` data to 1, 2, 3. `pollClick` indexes the *original* `items` array, so clicking row 2 (`b`) returns index 1 → fires `C`'s handler, and clicking row 3 (`c`) returns 2 → `items[2]` is undefined, so the click is silently dropped. The `count` argument (2) is ignored by C, so the mismatch is invisible to the caller: `tray.setMenu` answers `{ok:true, labels:["a\nb","c"]}`.
- reachable by: any page calls `tray.setMenu` with a label containing a newline (an ordinary multi-line status text). A user clicks the split row or the row after it; the wrong item's `onClick` runs or the right one never fires.
- smallest fix: reject `\n` in `readItems` (or escape it in the transport and unescape in C), and have `shim_tray_menu` stop at `count` rows so the table cannot disagree with the adapter's `items`.

## Silent lie — a surface "closed" at the C level leaves its empty `GtkFixed` wrapper in the window's overlay

- where: `src/platform/linux/shim/30_webview.c:147-154` (`shim_webview_close` calls `shim_host_forget` then `gtk_widget_destroy(web)`), `src/platform/linux/shim/42_host.c:20-29` (`shim_host_forget` only clears the two table slots), `:31-47` (`shim_host_for` creates a `GtkFixed` per view), `:54-80` (the host is added to the overlay as a child); `src/platform/linux/browser-ports.ts:103-105` (`close` → `shim_webview_close`)
- mechanism: `shim_webview_close` destroys the webview but never the `GtkFixed` that was added with `gtk_overlay_add_overlay` (`:61`) and carries the last size request and margins (`:70-75`). Destroying the webview removes it from its parent but leaves the wrapper as an empty overlay child. Each open/close cycle leaks one `GtkFixed` and leaves a stale rectangle in the overlay; `shim_host_forget` frees only the slot table entry, not the widget. The docs claim "closing a surface is `gtk_widget_destroy` — it removes the widget from the overlay itself, so no container keeps a child that is about to be freed" (`docs/agents/linux-platform.md:36`); the wrapper contradicts that.
- reachable by: page calls `browser.open` then `browser.close` in a loop (a docs panel toggled repeatedly). GTK keeps an empty positioned child per cycle; memory grows and the overlay accumulates an invisible child at each old rectangle.
- smallest fix: have `shim_webview_close` look up the host via `shim_webview_host(web)` and call `shim_widget_destroy(host)` (after the webview) before `shim_host_forget`; consider reusing a destroyed host's slot only after its widget is gone. A test should assert `shim_webview_host(web) == 0` and that the overlay's child count returns to its pre-open value.

## Wart — the per-view state table never frees a slot, so the 33rd view in a process loses load/eval state

- where: `src/platform/linux/shim/32_view_state.c:12` (`SHIM_VIEW_STATE_MAX 32`), `:31-32` (static table and count), `:41-62` (`shim_view_state_for`), `:64` (`shim_state_register`); `src/platform/linux/shim/30_webview.c:94-107` (register on every new view); `src/platform/linux/shim/30_webview.c:147-154` (close never unregisters)
- mechanism: the table uses `state->view` as the occupied marker and only ever sets it to a view pointer (`:56`). No code path writes `shim_view_states[i].view = 0`; `shim_webview_close` forgets the host slot but not the view-state slot. Once 32 WebKitWebViews have been created in the process, `shim_view_state_for(view, 1)` returns 0 for a new one, so `shim_webview_load_state` reports `0` (started) forever, `shim_webview_eval_state` reports `0` (pending) forever, and the eval proof never settles. The header comment (`:8-10`) claims "a slot is reused as soon as its view is gone" — nothing releases it. This also interacts with address reuse: a new view at a recycled pointer *does* inherit/reset the old slot via `shim_state_register`, which is the only reuse that happens.
- reachable by: a page creates and closes 33 browser surfaces (or 33 extra windows with their own webviews) over a session. `SurfaceStore` has no cap, and each `browser.open` calls `shim_webview_new` → `shim_state_register`.
- smallest fix: add `shim_state_forget(void *view)` and call it from `shim_webview_close` and from the window destroy path (`shim_on_destroy` cannot see child webviews, so release every surface in the platform before destroying the window, or clear records whose view is no longer in any slot). Test with 33 sequential opens and assert the 33rd load state changes from started to finished.

## Wart — a host created when all 32 host slots are taken is leaked

- where: `src/platform/linux/shim/42_host.c:31-47` — `host = shim_fixed_new()` at `:35`, then `if (slot < 0) return 0;` at `:43` without destroying `host`
- mechanism: the slot search happens after widget creation. With all 32 entries occupied, `shim_webview_place` returns 0 (`:58`), the adapter closes the view, but the new `GtkFixed` is never added to a container and never destroyed — a floating reference GTK holds until process exit. Combined with the missing release above (close does not free slots except via `shim_host_forget`), reaching 32 concurrent surfaces is enough, and every further failed open leaks one widget.
- reachable by: page opens 33 browser surfaces without closing any (no cap in `browser.ts:47-126`). The 33rd open fails with `handler-error: the container refused the rectangle`; repeat to grow the leak.
- smallest fix: find the slot before calling `shim_fixed_new`, or destroy `host` on the `slot < 0` branch.
