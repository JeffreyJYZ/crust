# Network, navigation and URL surfaces — hunt 21

Field: `src/plugins/network*.ts`, `navigation*.ts`, `deep-link.ts`, `downloads*.ts`, `opener.ts` and
their platform halves. Every claim is labelled `read` (code trace) or `measured` (ran locally).
No GUI, no e2e, no file edited except this report. Hunt-20 `05-url-surfaces.md` items are skipped
unless re-checked below.

## HIGH — The macOS runtime never supplies the WKWebViewConfiguration, so `crust:network` interception is dead in every built app

- where: `src/runtime-plugins.ts:114,187`; `src/runtime-network.ts:19-22`; `src/platform/darwin/network.ts:56,94-101`; `src/platform/darwin/webview-configuration.ts:21-28`; `src/platform/darwin/window-create.ts:80`
- mechanism: The macOS runtime builds the network plugin with `darwinNetworkPlugin()` and no options, so `darwinNetworkAdapter` gets `{}` and its `configuration` callback is `undefined`. `install` returns `{ ok:false, reason:"network.install needs the WKWebViewConfiguration…" }` before it builds the decision callbacks or calls `net_install`. The one configuration the process actually uses is created by `webviewConfiguration()` in `window-create.ts`, but that function is never passed to the adapter outside `network-probe.ts` (a dev-only probe). Result: no `WKURLSchemeHandler` is registered, every `crust-net:` request fails as an unknown scheme, and `setRules`/`log`/`clearLog` operate on a rule engine nothing consults. The docs promise the opposite — "It is registered by the macOS runtime with `darwinNetworkAdapter()`, so `window.crust.invoke("network", …)` works in an app that names no plugin" (`site/app/docs/guides/network/page.mdx:28`). `measured`: `darwinNetworkAdapter().install("crust-net", …)` returns exactly that refused object. `read`: the only production construction of the plugin is `runtime-plugins.ts:187`; `rg` finds `{ configuration }` only in `network-probe.ts:88`.
- reachable by: any built macOS app that calls `network.setRules` (the documented setup). `rules()`/`setRules()` answer `registered: false` with the refusal reason — honest, but the headline interception feature never runs. A page cannot recover: there is no command to hand the adapter a configuration after the fact.
- smallest fix: Wire `darwinNetworkPlugin({ configuration: webviewConfiguration })` in `runtime-plugins.ts` **and** install eagerly before the first webview is built (call `ready()` from `createNetworkPlugin` at construction, or register the handler in `webviewConfiguration()`), because WebKit refuses a handler on a configuration a webview already used (`docs/agents/window-webview.md:29`). Wiring alone is insufficient: the current lazy install fires on the first `setRules`, after the window exists.

## MEDIUM — A second `navigation.start` on one window deletes the first page's event listener, so navigation events stop for everyone

- where: `src/platform/darwin/navigation.ts:112-130`; `src/platform/darwin/shim/107_navigation.c:160-180` (`crust_nav_install` returns `4` when a crust delegate already exists)
- mechanism: `start` does `listeners.set(view, listener)` **before** calling native `crust_nav_install`. On a second `start` for the same webview the native call returns `4` (`alreadyInstalled`), so the code takes `if (status !== installed) listeners.delete(view)`. That removes the map entry for that view entirely. The native delegate is still installed and still fires `crust_nav_*` callbacks, but the process-wide sink finds no listener (`navigation.ts:76-77`) and drops every one. `measured`: driving `darwinNavigationAdapter` with a native fake that returns `0` then `4` gives first `start` `ok:true`, second `start` `ok:false`. `read`: the `listeners.set` precedes the install and the failure branch deletes rather than restores.
- reachable by: two pages (or a page re-registering after a reload) both call `crust.invoke("navigation","start")` on the same window. The second caller gets an `ok:false` naming "already installed" — with no hint that it just disabled the first caller's events. From then on `navigation:did-start/did-commit/did-finish/did-fail` never reach any page for that webview, though loads and `state()` keep working.
- smallest fix: Only `listeners.set(view, listener)` after a successful install; on `alreadyInstalled`, either keep the existing listener and return success, or restore the prior listener before returning the refusal — never delete the map entry for a still-installed delegate.

## MEDIUM — `deep-link.scheme` still always answers not-implemented, and the scheme guard stays disabled (re-check of hunt-20 #3, still open)

- where: `src/plugins/deep-link.ts:72-97,112`; `src/runtime-plugins.ts:133-135,191`; `src/app-loop.ts:123-124`; `src/config/types.ts:69`; `src/packaging/plist.ts:104-106`
- mechanism: Only `createDeepLink({ scheme })` sets `DeepLink.scheme`; the singleton `deepLink = createDeepLink()` is created with no options and is the instance both the runtime (`runtime-plugins.ts:135`) and `installLaunchDeepLink` (`app-loop.ts:124`) mount. `build.urlScheme` is validated and merged into `Info.plist`, but no production code passes it into `createDeepLink`. `read`/`measured` via `rg`: `urlScheme` appears only in `cli/build.ts`, `packaging/{app,plist}.ts`, `config/{types,validate-build}.ts` — never in a runtime/`createDeepLink` call.
- reachable by: any app that sets `build.urlScheme` and builds; a page calling `crust.invoke("deep-link","scheme")` gets not-implemented although macOS registered and routes the scheme. The `target.scheme !== scheme` rejection in `accept()` (`deep-link.ts:78-82`) is also permanently inert in production, so any absolute URL the delegate records is accepted.
- smallest fix: build one `DeepLink` from config (`createDeepLink({ scheme: config.build?.urlScheme })`) and mount that instance in both `runtime-plugins.ts` and `installLaunchDeepLink`.

## MEDIUM — Later deep links are still recorded but never delivered (re-check of hunt-20 #2, still open)

- where: `src/app-loop.ts:117-125`; `src/platform/darwin/deep-link.ts:100-115`; `src/plugins/deep-link.ts:43-47,76-87`
- mechanism: The C delegate stores every `application:openURLs:` URL in a static buffer (`shim/95_deeplink.c:53-67`). `app.run()` drains it once with `takeLaunchUrl()` (`app-loop.ts:121`) and calls `deepLink.launch(launched)` with **no ctx**, so even the launch URL emits no `deep-link` event. `takePendingUrl()` — the only reader of a later URL — still has no production caller. `read`/`measured` via `rg`: its only references are `deep-link.ts:109` itself and its test; `DeepLink.open()` is likewise only called in tests.
- reachable by: app already running; user clicks an app-owned `scheme://…` link; LaunchServices sends the Apple Event to the running app and the delegate stores it; nothing drains it. `deep-link.url()` keeps returning the launch URL forever and the documented `deep-link` event never fires — the plugin's stated headline ("every later one macOS delivers", `deep-link.ts:2`).
- smallest fix: In the pump tick (`app-watch.ts`/`app.ts`), drain `takePendingUrl()` and call `deepLink.open(url, ctx)` with a persistent app-wide emit sink, the way `navigation.ts:79-114` keeps one `sink`.

## LOW — An `allow` body at exactly `NETWORK_BODY_LIMIT` is accepted but its last byte is silently dropped

- where: `src/plugins/network-rules.ts:66-72`; `src/plugins/network-types.ts:35`; `src/platform/darwin/network.ts:78-88`; `src/platform/darwin/shim/113_network_serve.c:11,46-50`
- mechanism: `readBody` rejects a body only when `bytes > NETWORK_BODY_LIMIT` (262144), and the JS `fill` callback rejects only when `bytes.length > bodyCap` (also 262144), so a 262144-byte body is accepted and logged as served with 262144 bytes. In C, `net_serve` clamps `length > NET_BODY - 1` to 262143 before `initWithBytes:length:`, so WebKit delivers 262143 bytes. The docs promise a body over the buffer is "refused rather than truncated", but the off-by-one puts the last valid byte in the truncated zone. `measured`: `setRules` accepted a 262144-char body and `decide()` returned all 262144 bytes; `read`: the C clamp to `NET_BODY - 1`.
- reachable by: a page sets a rule whose `body` is exactly 262144 ASCII characters (the documented maximum), requests it, and reads a response missing its final byte; `log()` still reports the full count.
- smallest fix: make the validator's limit `NETWORK_BODY_LIMIT - 1` (or drop the C clamp and reserve the NUL outside the byte count) so the accepted maximum matches the number of bytes actually delivered, and keep `log()`'s `bytes` honest.

## Checked and clean

- **Navigation allowlist vs. a redirect**: the origin allowlist is not in my field. It lives in `crust:browser` (`src/config/types.ts:168-175`, `src/plugins/browser*`) — lane 03's field — and lane 03 already reported the "allowed page can redirect the surface to any origin" gap. `navigation.loadUrl` itself has no scheme/origin filter by documented design (hunt-20/05 "Checked and clean": arbitrary top-level navigation is a normal first-party action). No duplicate finding.
- **Interception rule bypass via URL truncation**: the chain is fail-closed. `net_copy` keeps at most 2047 bytes (`shim/110_network.c:42-53`), the darwin read buffer is 2048 (`network.ts:34`), and `judge` refuses any URL whose UTF-8 byte length is >= 2047 before matching (`network.ts:87-98`) — a tail-anchored `block` rule cannot be dodged with a long query. `measured` chain in `network-url.test.ts:35-80`. `read`: rule validation is atomic (`network-rules.ts:86-111`), and the matcher is a bounded glob (<=32 stars, no regex), so no catastrophic backtrack and no unvalidated rule reaches the handler. I found no bypass beyond the body off-by-one above.
- **URL parsing / scheme confusion in `crust-net`**: interception covers only the registered scheme; `caseInsensitive` folds both sides on darwin/win32, closing a host-case dodge (`network-match.ts:18-27`). Linux keeps byte-wise compare, but no WebKit handler exists there, so the path is unreachable — I did not claim it. Consecutive/leading/trailing `*` semantics were checked against `network-pattern.test.ts` and match correctly.
- **Opener handing a URL to the OS**: `SCHEME` (`^[a-z][a-z0-9+.-]*:`) gates a non-empty URL, then `crust_opener_open_url` passes it to `+[NSURL URLWithString:]` and NSWorkspace with any scheme — a documented design choice, not a defect (hunt-20/05, same conclusion). `openPath`/`revealItem` resolve to an absolute path and refuse a missing one before any AppKit send (`opener.ts:83-86,141-145`); an adapter throw becomes a typed `handler-error`, never `ok:true`.
- **Deep-link parsing**: `parseDeepLink` uses `new URL`, lowercases the scheme and reads `hostname`/`pathname`; a `?__proto__=x` key passes a string to the inherited setter and is silently dropped, not a pollution vector (hunt-20/05). The argv scan `dl_is_url` requires 2+ scheme chars before `:` so a drive letter or path cannot match (`shim/95_deeplink.c:121-151`). Launch dispatch runs before the first window (`app.ts:161-162`), so there is no "before ready" race for the launch URL itself.
- **Downloads to an unchecked path**: `destination()` refuses relative paths, collapses `..`, and compares canonical forms of both root and target, including dangling symlinks via `readlink` with a cycle guard (`downloads-scope.ts:40-83`). `uniquePath()` strips `/` and `\` from the server-suggested filename and reserves each answer, so a traversed or duplicate name cannot land outside the checked directory (`platform/darwin/downloads.ts:54-75`). No unchecked path found.
- **Navigation label/URL resolution**: `target()`/`loadArgs()` validate a non-empty label and non-empty URL before any native call, and an unknown label keeps the resolver's `bad-request` rather than falling back to the first window (`navigation-target.ts:39-68`); this is unchanged from hunt-20/05's clean finding.
- **Shared native globals under concurrent requests (caveat, not filed)**: the darwin network adapter keeps one `reply` and one C `net_text` across all tasks (`network.ts:64`, `shim/110_network.c:29`). Two simultaneous `crust-net:` fetches could in principle cross-talk. I could not establish WebKit's `startURLSchemeTask` threading without a GUI probe (forbidden here), and the handler is never installed in a built app anyway (finding #1), so I report no finding — a reviewer with a live probe should check this if finding #1 is fixed.
