# Updater hunt

Field: `src/plugins/updater-*.ts` (archive, args, artifact, bundle, download, fetch, install, manifest,
node, receipt, relaunch, signature, slip, url) and `src/plugins/updater.ts`. Prior round:
`docs/reviews/hunt-20/10-packaging.md` covers the packaging CLI and touches no updater code;
`hunt-20/22-error-paths.md` filed the `replaceBundle` rollback being swallowed (`updater-node.ts:145-154`),
still unfixed, not re-reported here — the one item I add beside it is the *answer shape*, below.

Every claim is labelled `measured` (I ran a `bun -e` probe) or `read`.

## High — A pinned `updater.pubkey` does not require a signature: an unsigned artifact installs
- where: `src/plugins/updater-download.ts:42-47` and `:52-60`; `src/plugins/updater-signature.ts:74-84`
- mechanism: `readSignatureArgs` answers `undefined` when the `download` arguments carry no `signature`, and `runDownload` then skips the whole verify block (`if (signed !== undefined)`) and records a receipt. The pinned key is consulted only when a signature happens to be claimed, so `updater.pubkey` is an option the caller may omit rather than a gate. The one mandatory check is `sha256`, and the manifest supplies that same value, so a hostile update server that answers for both the manifest and the artifact chooses both halves. The docs frame `pubkey` as "needed for any signature" rather than as required, but `updater.ts:3` and `api-updater/page.mdx:5` state the flow as "nothing is installed that this run did not verify", and for an app that pinned a key that sentence is not true of an unsigned artifact.
- reachable by: `measured`. Config `updater: { endpoint, pubkey }`; manifest `{ version: "9.9.9", url: "https://evil.test/Notes.app.zip", sha256: <attacker digest> }`; page calls `download({ url, sha256 })` with no `signature`, then `install({ path, appPath })`. My probe returned `{"ok":true,"path":"…/crust-update-…/Notes.app.zip","bytes":21,"sha256":"5ed38f…"}` for a payload the pinned key never signed, and a second probe drove `install` to `{ ok: true, appPath, backup }` with the attacker's bundle at `appPath` (its `marker.txt` read back `ATTACKER`). Nothing in either run consulted the key.
- smallest fix: when `options.pubkey` is set, treat a missing `signature` as a named refusal (`requires: "updater.pubkey"`) instead of a valid unsigned download; leave the unsigned path only for apps that pinned no key, which is the case the guide already describes as unverified.

## Medium — A symlink entry redirects later writes, so the tree `install` renames is not the archive's entry list
- where: `src/plugins/updater-node.ts:111-126` (entries written in archive order); `src/plugins/updater-slip.ts:44-65` (`assertLinkInside` resolves its own target lexically only)
- mechanism: `extractZip` writes entries in order, and both `mkdir(dirname(path), { recursive: true })` and `writeFile` follow a symlink an earlier entry created. `assertLinkInside` checks each target against the *entry's own name* only, so a link to a directory inside the bundle is accepted — and every later entry under that name is then written through the link. `install` re-hashes the resulting tree and the archive, so both digests are self-consistent and nothing refuses; the tree that gets renamed is not the tree the archive's entry names describe.
- reachable by: `measured`. An archive with `Notes.app/Contents/MacOS/Notes` (`#!/bin/sh\necho real\n`, mode `0o755`), then `Notes.app/Contents/evil` as a symlink to `MacOS`, then `Notes.app/Contents/evil/Notes` (`#!/bin/sh\necho PWNED REPLACES THE BINARY\n`, mode `0o755`). `download` answered `{ ok: true, …, archive: { … } }`, and the extracted `Contents/MacOS/Notes` read back as `"#!/bin/sh\necho PWNED REPLACES THE BINARY\n"` — the later entry silently replaced the executable the earlier one declared. This is not an escape from the bundle: I checked the obvious chains (`d` → `.`, `d` → `..`, a later name containing `..`) and `assertLinkInside` plus `assertEntryName` refuse each, so nothing is written outside the `.app`. The cost is integrity inside it — a bundle can gain or lose files, including its own executable, with no refusal, and the digest `download` records describes the wrong tree.
- smallest fix: refuse an entry whose parent chain contains a symlink an earlier entry emitted — the rule `unzip` and `tar --no-overwrite-dir` use. Cheapest correct form: after `assertLinkInside`, reject the archive when any ancestor of `entry.name` in the entry list has `kind === "symlink"`.

## Medium — A launch failure after a successful swap is reported inside an `ok: true` body
- where: `src/plugins/updater.ts:151-157`
- mechanism: once `replaceBundle` has landed, `install` calls `start(appPath)` and, on a throw, returns `{ ok: true, appPath, backup, relaunchError }`. A caller that checks `ok` — and the bridge's own `resultStatus` (`src/bridge/server/failure-status.ts:35-41`) — reads that as success and sends HTTP 200, so the one case where the app did not come back up is indistinguishable at the transport level from a clean install. `InstallResult`'s doc comment calls the shape deliberate and rolling the swap back would be worse; the defect is the shape, not the decision.
- reachable by: `updater.install({ path, appPath, relaunch: true })` where `open -n` refuses — the new bundle's executable is not runnable, LaunchServices is busy, or the bundle moved between the swap and the launch. `updater-relaunch.test.ts:131-161` asserts exactly this body and calls it correct.
- smallest fix: keep the swap landed but answer `{ ok: false, code: "relaunch-failed", appPath, backup, installed: true }`, so `ok` means "the app is running the new build"; or add an explicit `running: boolean` to `InstallResult` and have the guide tell a page to branch on it.

## Medium — A deflated entry inflates with no bound, so a 512 MB download can become hundreds of gigabytes
- where: `src/plugins/updater-archive.ts:96-106` (`dataOf`), `:117` (the central directory's uncompressed size at `+24` is never read); `src/plugins/updater-fetch.ts:16` (`MAX_DOWNLOAD_BYTES` caps only wire bytes)
- mechanism: `readBounded` caps the *compressed* body at 512 MB, and `dataOf` then hands the raw deflate stream to `Bun.inflateSync` with no output limit. The central directory's uncompressed length sits at `+24`, which the reader never reads, so a declared size is neither checked nor used as a bound.
- reachable by: `measured`. A 32,769-byte archive inflated to 33,554,432 bytes in 14 ms — 1024x, the deflate maximum — and a 367-byte archive inflated one entry to 204,800 bytes (558x). 512 MB of deflate at that ratio is ~512 GB of allocation, and the bytes are then retained in `chunks`/`entries` and written to disk. A hostile or mistaken update server reaches it: `download` verifies the digest and any claimed signature over the *compressed* bytes, then calls `materialiseArtifact` → `extractZip` → `readArchive`, and a validly signed but highly compressible archive is accepted. A test app with `updater.allowFileUrl` reaches the same path from a local file.
- smallest fix: read the central directory's uncompressed size (`view.getUint32(at + 24, true)`) and refuse an entry whose declared size, or a running total across entries, exceeds a cap; `Bun.inflateSync` has no `maxOutputLength`, so the declared size plus the running total is the available bound.

## Medium — `install`'s answer cannot say the old bundle is gone when the rollback also failed
- where: `src/plugins/updater-node.ts:140-150`; `src/plugins/updater.ts:158-160`
- mechanism: `replaceBundle` renames the live bundle to `backup`, then renames `source` into place; on a forward-rename throw it runs `rename(backup, real).catch(() => undefined)` and rethrows the *original* error. `install`'s catch turns that into `{ ok: false, code: "install-failed", message }` naming only the forward rename. hunt-20 filed the swallowed rollback; what is not in that report is that no answer shape distinguishes "the swap never started" from "the swap landed and the restore failed", so the page is told a rename failed while the app at `appPath` is absent and the only copy is at `<appPath>.old`.
- reachable by: a forward `rename` that throws without also clearing the rollback — a transient EXDEV, the destination becoming occupied between the two calls, or the volume going read-only in that window.
- smallest fix: await the rollback, and on its failure throw an error naming both failures plus `backup`; give `install` a distinct code or an `installed: false, parkedAt: <backup>` field, so "nothing moved" cannot be confused with "moved, then the restore failed".

## Low — `fetchJson` reads a manifest with no byte cap at all
- where: `src/plugins/updater-node.ts:57-65`; the bound it should use is `readBounded` in `src/plugins/updater-fetch.ts:22-48`
- mechanism: `download` routes its body through `readBounded`, but `fetchJson` calls `fetchFollowing(url, { headers … })` and then `await response.json()` with no limit. A manifest endpoint that streams a body with no `content-length`, or simply never closes, is read to completion — the module header at `updater-fetch.ts:2-4` claims "the two bounds `fetchJson` and `download` need", and only one of them has it.
- reachable by: a manifest host that never ends its response. `check` is on the startup path for an app that follows the guide's `autoCheck` shape, so this is the first network call the app makes; the peer arm, `download`, is capped at 512 MB.
- smallest fix: `readBounded(response, url, MANIFEST_CAP)` before `response.json()`, with a cap of a few hundred KiB — a manifest is one small JSON object.
- checked and clean on the same path: `readBounded`'s streaming arm is correct — `measured` by reading the order, it tests `total > limit` *before* `chunks.push(chunk)`, so an over-cap chunk is never retained; only the in-cap prefix is buffered, and the `content-length` pre-check refuses a declared oversize before the body is read.

## Low — Every download and extraction leaves its temp directory behind forever
- where: `src/plugins/updater-node.ts:91-93` (`makeTempDir`), `:110` (the extract dir); no `rm` of either anywhere in `src/plugins/updater*`
- mechanism: `download` writes into a fresh `mkdtemp` and `extractZip` into another, and nothing ever removes either — `rg` over the updater files finds exactly one `rm`, the `.old` backup at `updater-node.ts:141`. macOS does not sweep the per-app `/var/folders` temp dir on a schedule the way `/tmp` is swept, so the leak lasts for the life of the volume.
- reachable by: `measured` on this machine: 5,196 `crust-update-*` directories and 579 `crust-extract-*` directories in the approved temp dir, 4,044 and 386 of them non-empty. In a shipped app each holds a full copy of the update, tens of MB, and the counts grow with every check that downloads.
- smallest fix: delete the extract dir once `materialiseArtifact` has answered (the tree it names must survive until `install`, so move it out or record it for cleanup), and delete the download dir after a successful `install`; a `finally` in `runDownload` covers the refusal paths.

## Low — The pinned key and the manifest's key are compared as text, so two spellings of one key disagree
- where: `src/plugins/updater-signature.ts:11-18` and `:36-40`; `src/config/validate-updater.ts:5-6,19-22`; `src/plugins/updater.ts:102-107` and `updater-signature.ts:81-82`
- mechanism: `pubkey` equality is a string compare, and `BASE64_32` accepts a 43-character unpadded key and its 44-character padded form alike. Those two strings are different text for the same 32 bytes: `measured`, across 4,000 random keys the unpadded form was accepted every time and decoded to identical bytes every time, while `canon === unpadded` was false and `Buffer.from(canon)` equalled `Buffer.from(unpadded)`. So an app pinned to the padded spelling refuses a manifest that publishes the unpadded spelling of the same key: `measured`, `check` answers `bad-manifest` ("the manifest's pubkey is not this app's") and `download` answers `invalid-arguments` ("refuses a pubkey that is not this app's"). Both are false statements about a genuine update, and the `check` refusal is the one a page sees first.
- reachable by: a manifest generator emits the unpadded form — many do, since 43 characters is what `openssl rand -base64 32` produces once the trailing newline is stripped — while the app pins the padded form, or the reverse. Config validation passes both, and every real signature is refused.
- smallest fix: compare the two keys as decoded bytes over 32 bytes rather than as text, and require the canonical spelling in `validateUpdater` so an app's own key is normalised once at startup.

## Low — A non-canonical `pubkey` in the config is accepted and imports as a different key
- where: `src/plugins/updater-signature.ts:11-18,36-40`; `src/config/validate-updater.ts:5-6,19-22`
- mechanism: `BASE64` matches any run of alphabet characters with up to two `=`, and `Buffer.from(value, "base64")` decodes a length that is not a multiple of four by dropping the dangling character's low bits. `measured`: `"A".repeat(43)` passes both `BASE64` and `BASE64_32`, decodes to 32 bytes, and re-encodes to 44 characters — so it imports as *some* 32-byte Ed25519 key whose bits the author never published, `verifyEd25519` answers `false` for every signature by the key they hold, and `runDownload` reports `signature-mismatch`: "the artifact does not match the manifest signature". The app blames the update for a broken key.
- reachable by: an author hand-edits `updater.pubkey` and drops a character, or pastes a value from a tool that emits an odd form. The validator accepts it, so the fault surfaces only later as a tamper warning on a legitimate update.
- smallest fix: require canonical base64 in `decodeBase64` (`bytes.length > 0 && Buffer.from(bytes).toString("base64") === value`) and have `validateUpdater` refuse a non-canonical `pubkey` at startup, so a bad key is a config failure rather than a false `signature-mismatch`.

## Low — A hostile entry that collides on disk, or a link that loops, answers `download-failed` with a raw Node error, not `invalid-archive`
- where: `src/plugins/updater-node.ts:110-127` (the extraction loop) and `:79-87` (`sha256` → `digestTree`); the contract it breaks is `src/plugins/updater-types.ts:96-101`
- mechanism: only `readArchive`'s own throws are wrapped as `invalid-archive`. A `mkdir`/`writeFile`/`symlink` failure, and a `stat` that walks into a symlink cycle, escape as raw Node errors, and `runDownload`'s catch turns each into `{ ok: false, code: "download-failed", message: "EEXIST: …" }` or `"ELOOP: too many symbolic links encountered, stat '…/Self/Contents/Self/…'"`. The adapter's documented contract says a hostile entry throws `invalid-archive`; these do not, and the message carries the extraction path.
- reachable by: `measured`, twice. (a) A symlink `Notes.app/Contents/alias` → `real.txt` followed by `Notes.app/Contents/alias/planted.txt` made `mkdir` fail `EEXIST` (the link resolves to a file, not a directory). (b) A symlink `Notes.app/Contents/Self` → `..` is **accepted** by `assertLinkInside` — its target normalises to the archive root, so it passes — and `digestTree` then recurses `Contents/Self/Contents/Self/…` until `stat` answers `ELOOP` after 28 ms. The cycle is bounded by the path limit rather than by a check, so it costs a confusing refusal rather than a hang, but a deeper link chain costs proportionally more.
- smallest fix: wrap the whole extraction loop *and* the `digestTree` walk in the same `try`/`catch` that wraps `readArchive`, so any per-entry failure answers `invalid-archive` naming the archive and the entry; and reject a symlink whose target normalises to the root or to any of its own ancestors, which is the cycle `assertLinkInside` currently admits.

## Checked and clean

- **Redirect and TLS policy** (`updater-fetch.ts:50-103`): `read`. `redirect: "manual"` on every hop, a `location` that is not `https:` refused before any request for it, `MAX_REDIRECT_HOPS` counted, and a redirect with no `location` refused by name. `fetchJson` and `download` share the same `fetchFollowing`, so `check` cannot be the plaintext hole `download` is not. The initial hop of a `file:` URL is the one non-https path and is gated by `updater-url.ts` on `updater.allowFileUrl`. The boundary is the signature over bytes, not the host, which is why the missing-signature gate above matters.
- **Scheme policy** (`updater-url.ts:22-44`): `read`. `https:` only; `file:` only with the opt-in, carrying `requires`; every other scheme refused naming the scheme. `check` passes `"check"`, so the refusal names the right command (`updater.ts:83-88`).
- **Signature verification when a signature is claimed** (`updater-download.ts:42-60`): `read`. `sha256` mandatory, a signature with no pinned key is `requiresPubkey`, a page-supplied `pubkey` differing from the pinned one is refused, the check runs over the downloaded bytes before `materialiseArtifact`, and `receipts.record` runs only after both. No path verifies against a page-supplied key.
- **Zip name rules** (`updater-slip.ts:25-41,68-81`): `read`, with `updater-archive.test.ts:38-85` `measured` by its assertions — absolute, `..`, backslash, NUL and a nested climb each refused by name before a byte is written; exactly one top-level `.app` root. I also probed a root-level symlink entry (`Notes.app` → `Contents`): refused as "pointing outside the archive".
- **Zip reader input bounds** (`updater-archive.ts:56-168`): `read`. Every offset is `assertRange`-checked before it is read, so a truncated or hostile archive answers `invalid-archive` rather than a `DataView` `RangeError`; zip64 and encrypted entries are refused by name; only stored and deflate are read. The gap that remains is the *output* bound, filed above.
- **Install target selection** (`updater-bundle.ts:16-49`, `updater.ts:113-131`): `read`, with `updater-install-target.test.ts` `measured`. `install` refuses a non-`.app` target, then a target whose `realpath` is not this process's own bundle, then a non-`.app` source, then re-hashes both halves of the receipt — and only then renames. `ownBundleOf` requires the `Contents/MacOS` shape, so a dev run refuses; `replaceBundle` resolves a symlinked `appPath` and renames the real bundle.
- **Receipt before the new bundle is in place** (`updater-receipt.ts:35-43`, `updater.ts:120-152`): `read`. Per plugin instance, in memory, keyed by `resolve(path)`, so no cross-run replay and no alternate spelling; both the archive and the tree digests are re-checked before the swap, and `updater-archive-install.test.ts:91-136` asserts each arm.
- **Relaunch after replace** (`updater.ts:151-157`, `updater-bundle.ts:52-66`, `updater-node.ts:153-164`): `read`. Same own-bundle gate, runs only after the swap, and `open -n` takes the path so a still-running copy cannot answer for the replaced bundle; `updater-relaunch.test.ts:106-161` asserts both arms.
- **`fileNameFor`** (`updater-args.ts:186-190`): `read`. Last path segment reduced to `[A-Za-z0-9._-]`, `.`/`..`/empty rejected, so a hostile URL cannot name the file it becomes.
- **Version comparison** (`updater-args.ts:78-113`): `measured`. `0.10.0 > 0.9.0`, `1.0.0 > 1.0.0-beta.1`, `1.0.0-alpha < 1.0.0-alpha.1`, `banana < 1.0.0` — numeric per segment with a bare release above its tags. A 20-digit segment exceeds `Number.MAX_SAFE_INTEGER` and rounds (`1.99999999999999999999` compares as `2.0.0`), but a manifest cannot use that to *downgrade*, so it is a wart and not a finding.
- **Manifest strictness** (`updater-manifest.ts:9-38`): `read`. Unknown field shapes refuse with the reason; `signature`/`pubkey` only as a pair and only when both decode; `sha256` must be 64 hex and is lowercased.
- **Platform gate** (`updater.ts:114,163`, `updater-platform.test.ts`): `read` plus that test's assertions. `install` and `relaunch` refuse by name off darwin before touching disk; `check` and `download` are platform-neutral.
- **Argument handling** (`updater.ts:115-121`, `updater-args.ts:171-175`): `read`, with `measured` confirmation that a whitespace-only string reads as absent, so neither `path` nor `appPath` can be `""` or `"   "`.
- **`updater.config`** (`updater.ts:69-74`): `read`. Reports only the four documented keys, with booleans coerced by `=== true`; it cannot set anything.
- **Not run**: no build, no test suite, no e2e, no GUI. Nothing here is a runtime observation on Windows or Linux.
