# Shell chrome — hunt 21

All claims below are `read` (code inspection) unless marked `measured`. No GUI, e2e or native call was
run; the one `measured` line is a pure-parser probe with `bun -e`.

## High — a context menu rewrites the live app menu's id table, so the wrong command fires
- where: `src/platform/darwin/menu-api.ts:34` (`let ids`), `:101-106` (`build`), `:109-116` (`setAppMenu` / `showContext`)
- mechanism: `build()` does `ids = []` then `addRows(unit, items, ids)` pushes the new rows' ids into that same module-level array. Every native row carries a numeric `tag` that is an index into `ids`; the one click trampoline resolves `ids[tag]` (`:75-77`). `setAppMenu` builds and installs the bar; `showContext` builds a *different* menu and reassigns `ids` to it, but the already-installed bar keeps its old tags and is never rebuilt. The next app-menu click indexes the context menu's id list.
- reachable by: `menu.setAppMenu({items:[{label:"Save",id:"save"},{label:"Quit",id:"quit"}]})` → user right-clicks → `menu.showContext({items:[{label:"Copy",id:"copy"}]})` → user clicks **Save** in the still-installed bar. Its tag `0` now reads `ids[0] === "copy"`, so the page receives `menu` `{id:"copy"}` and runs the wrong action; a click on **Quit** (tag 1) reads `undefined` and is silently dropped. The same corruption follows any failed rebuild: `build()` clears `ids` before `addRows`, so a throw mid-build (e.g. a spec deeper than C's `MENU_MAX_DEPTH 8`, `98_menu_api.c:145-146`, or a refused `menu_api_begin`) leaves the live bar pointing at a partial or empty table. `reset()` then clears `ids` while installing the default bar (`menu-api.ts:117-121`), which is safe only because the default bar's rows carry no `crustMenuSelected:` target (`55_menu.c`).
- smallest fix: keep one id table per built menu, and have each native row carry the table identity (or its literal id) so the click trampoline resolves against the menu the row belongs to; only swap the app-menu table in `setAppMenu`/`reset`, never in `showContext`. Leave the previous table intact until a replacement install succeeds.

## Medium — find/repeat in one window searches for another window's text
- where: `src/platform/darwin/shim/108_find.c:37` (`static find_t find_last`), `:118-131` (`crust_find_search`), `:145-156` (`crust_find_repeat`); `src/platform/darwin/find.ts:120-165`
- mechanism: C retains a single `find_last` string process-wide, replaced by every `crust_find_search`. `crust_find_repeat` sends that one string to whichever webview the command names. The TS half keeps `matchCase` per webview pointer (`find.ts:125`) but has no per-webview text, so its own comment — "a repeat re-runs that window's own search, so two windows cannot overwrite each other's flag" — is false for the query itself.
- reachable by: window A `findinpage.search({text:"alpha"})`, window B `findinpage.search({text:"beta"})`, then `findinpage.next({label:A})`. Window A repeats **beta** with A's case flag and reports a match from a search its user never typed. A reload does not clear `find_last`, so a `next()` after navigation also re-runs the pre-navigation query; a closed window's `matchCase` entry is never removed from the Map and a recycled `WKWebView` address inherits it.
- smallest fix: key the retained query and case flag by webview pointer in the C unit (with release on replace) and pass that entry to `crust_find_repeat`, or refuse `next`/`previous` for a webview that has not run its own `search`.

## Medium — an overlapping find completion answers the newer search
- where: `src/platform/darwin/find.ts:34-38` (single `pending`), `:45-62` (`channel` sink), `:65-107` (`supersede` / `ask`)
- mechanism: the JS completion sink takes whatever `pending` currently is and settles it. `supersede()` clears `pending` and rejects the older *promise*, but it cannot cancel the older WebKit find already in flight. The older completion still arrives and settles the **new** pending with its own `matchFound`; the newer completion then finds `pending` undefined and is dropped.
- reachable by: two find commands before either completion lands — e.g. a slow page, `findinpage.search({text:"foo"})` then `findinpage.search({text:"bar"})` from a second window. The second call's promise resolves with the **first** query's result. The 4 s timeout path (`ask`, `:99-107`) creates the same hazard: the timed-out completion can settle a search started after the timeout.
- smallest fix: echo a monotonically increasing request id from JS through the C sink (one extra int) and have the sink settle only the pending whose id matches, discarding stale completions.

## Medium — repeated `sleepPrevent` leaks the first assertion and `sleepAllow` reports it released
- where: `src/platform/darwin/shim/105_power.c:133` (`static pw_assertion`), `:139-158` (`crust_power_prevent_sleep`), `:163-176` (`crust_power_allow_sleep`); `src/plugins/power.ts:124-144`
- mechanism: `crust_power_prevent_sleep` overwrites `pw_assertion` with the new IOKit id without releasing the one it held. `crust_power_allow_sleep` releases only the current id. The plugin answers `{ok:true,id}` for every `preventSleep` and `{ok:true,released:true}` for one `allowSleep`, so both callers believe the machine can sleep.
- reachable by: two features (or two windows) each call `power.sleepPrevent({reason:...})`, then one calls `power.sleepAllow()`. Assertion 1 is never released — idle sleep stays prevented for the life of the process — and there is no command to release it by id, despite `SleepPreventResult` documenting the id as "for a caller that wants to prove which one it holds". The exit handler (`power.ts:104-113`) calls `crust_power_allow_sleep` once, so it only frees the last id.
- smallest fix: refuse a second `preventSleep` while one is held (returning the existing id), or store every id and have `allowSleep` release all of them.

## Medium — shortcut unregister drops its bookkeeping before the OS agrees
- where: `src/platform/darwin/shortcuts.ts:148-164` (`unregister`, `unregisterAll`); `src/plugins/shortcuts.ts:124-150`
- mechanism: the adapter deletes `ids` and `byId` *before* calling native `shortcut_unregister(id)`, then returns the C status. On failure the plugin keeps the accelerator in `live` (its comment says "so a retry reaches the OS again"), but the adapter has forgotten it: a retry returns `false` immediately, and a press still reaches the C trampoline whose `byId` lookup is now empty, so no `shortcut` event fires. C compounds it by clearing `shortcut_refs[i]` even when `UnregisterEventHotKey` fails (`93_shortcuts.c:98-108`), so `unregisterAll` cannot clean up later either. `unregisterAll` has the same shape: it clears both maps, swallows a thrown unit into `0`, and the plugin still clears `live` and answers `{removed:0}`.
- reachable by: `shortcut.register({accelerator:"Cmd+K"})`, then `shortcut.unregister({accelerator:"Cmd+K"})` when `UnregisterEventHotKey` returns non-zero (stale/invalid ref) or `shortcutUnit()` throws. `shortcut.list()` still shows the key, `isRegistered` is true, but the key can never be removed and never emits.
- smallest fix: delete from `ids`/`byId` only after native unregister returns success; keep the native ref when C refuses so a retry or `unregisterAll` can still reach it; report a thrown `unregisterAll` as a failure instead of `{removed:0}`.

## Medium — a bare key is accepted as a global hotkey
- where: `src/plugins/shortcut-accelerator.ts:78-107` (`parseAccelerator`); `src/platform/darwin/shortcuts.ts:132-134` (modifier mask); `src/platform/darwin/shim/93_shortcuts.c:82-93` (`shortcut_register`)
- mechanism: unlike `menu-spec.ts:89-95`, which explicitly refuses a bare key because it "would swallow ordinary typing", the shortcut grammar never checks `seen.length`. A key-only accelerator parses to `modifiers: []`, the mask folds to `0`, and `RegisterEventHotKey(keycode, 0, ...)` registers the key globally with no modifier. Every press of that key in every app is captured by the crust process.
- reachable by: `shortcut.register({accelerator:"k"})` — **measured**: a pure `bun -e` call to `parseAccelerator("k")` returned `{accelerator:"k",key:"k",modifiers:[]}`; the same probe on `menu-spec`'s parser rejected `"k"`. The native registration path is `read`, not measured.
- smallest fix: require at least one modifier in `shortcut.parseAccelerator`, with a `bad-accelerator` error naming the token, matching the menu grammar.

## Low — `isDefault` is a shape check, so a caller-built bar can claim to be the default
- where: `src/platform/darwin/shim/98_menu_read.c:131-142` (`menu_api_is_default`); `src/platform/darwin/menu-readback.ts:38-40`
- mechanism: identity is inferred from "exactly two roots and the first root's title equals `appName`". No pointer or marker distinguishes crust's `55_menu.c` bar from a page-built one.
- reachable by: `menu.setAppMenu({items:[{label:<appName>,submenu:[{label:"About"}]},{label:"Edit",submenu:[{label:"Copy"}]}]})` from a page that knows the app name (`os` exposes it), then `menu.isDefault()` answers `{ok:true,isDefault:true}` although the bar is caller-built and the documented default ⌘C/⌘V/⌘Q rows are gone.
- smallest fix: record the pointer of the bar installed by `shim_menu_install` in C and compare identity; clear it when `menu_api_install` installs a different bar.

## Low — `theme.current` throws instead of answering, and `set` flips `override` before verifying the readback
- where: `src/plugins/theme.ts:48-51` (`state`), `:58-72` (`apply`), `:78` (`current`); `src/platform/darwin/theme.ts:69-75` (`current` throws when C returns -1)
- mechanism: `current` calls `state(native)` outside any `try`, so a failed native read escapes as a rejected invoke, unlike `set`/`reset`, which convert it to a typed `ThemeFailure` — against this file's own "A refused AppKit call is a typed failure, not a rejected invoke" rule. In `apply`, `override` is assigned immediately after `target.set`, before `publish(ctx, state(target))` reads the appearance back; if that read throws, the command returns `ok:false` but the override flag is already set and the native appearance is already changed.
- reachable by: an effective appearance whose name contains none of `Dark`, `Aqua`, `Light` (`103_theme.c:56-62` returns -1) — e.g. an unusual accessibility or third-party appearance. `theme.set({appearance:"dark"})` then reports failure while having applied the theme; a following `theme.current()` rejects rather than returning a value.
- smallest fix: wrap `current` in the same `attempt`/`failureOf` path, and assign `override` only after `state(target)` succeeds (read back first, then publish).

## Low — `dock.badgeLabel` answers `ok:true` with an empty label when the native unit is unavailable
- where: `src/platform/darwin/dock.ts:76-82` (`compiled()` failure returns `""`); `src/plugins/dock.ts:106-109`
- mechanism: every other dock call returns a refusal with the compile reason, but `badgeLabel()` returns `""`, which the plugin passes through as `{ok:true,label:""}`. A native read that never happened is indistinguishable from "no badge".
- reachable by: a machine where the dock C unit fails to compile (missing AppKit or TinyCC failure) — `dock.badge`, `dock.bounce` and `dock.progress` all refuse, while `dock.badgeLabel` alone reports success.
- smallest fix: have the adapter return a failure/refusal on a compile error (or let the plugin call a `compiled()`-style guard), and only answer `{ok:true,label:""}` when the native read actually returned empty.

## Checked and clean
- **menu spec and accelerator grammar** (`menu-spec.ts`): `rg`-read all of `planRow`/`parseAccelerator`/`readPoint`; duplicate selectable ids, non-printable keys, bare keys, repeated modifiers, separators with submenus and non-finite context points are refused with the named code and verbatim `part`. Container ids are deliberately not registered because containers carry no action. The four modifier masks in `menu-api.ts:19-24` match `NSEventModifierFlags`.
- **menu readback** (`menu-read.ts`, `98_menu_read.c`): flat rows are reassembled by parent index with out-of-range parents kept at the root; strings are copied out of a bounded static buffer before the next call; `-1` (no bar) and `0` (empty bar) are distinct in C and collapse to `[]` in TS, which is honest for a caller that only needs the rows. The depth-8 menu cap and 64-row/256-byte read caps are documented limits that fail or truncate visibly rather than silently.
- **tray lifetime** (`status-bar-item.ts`, `status_bar/*.c`): one live item per process is enforced; `setMenu` copies the entry array before building so a caller mutation cannot change a click target; `destroy` clears `entries`, `clickRoute` and the slot; the title is read back and compared when the value fits the buffer; a missing `setToolTip:` is named as `not-implemented` rather than faked. The trampoline is intentionally never closed while rows point at it.
- **clipboard** (`clipboard*.ts`, `90_clipboard.c`, `101_clipboard_image.c`): write verdicts come from `setString:forType:`/`setData:forType:`, `null` (no pasteboard) is separate from `""` (empty), PNG magic is validated before a write, and the two-pass read re-reads at the exact length with a documented clamp for a pasteboard changed between passes. Reads/writes use the general pasteboard with no per-window scope, which is the documented contract on macOS.
- **screen/positioner geometry** (`screen.ts`, `97_screen.c`, `positioner.ts`, `windows/window-positioner.ts`): AppKit frames are read per call and flipped once at the seam with the primary's frame height as ceiling; the darwin positioner uses the visible frame in AppKit's y-up space with the default `up` axis, Windows passes `down` with `rcWork`; a missing or non-positive frame is refused rather than placing a window at 0,0. `screen.clean` drops unusable records and `primary` falls back to the first listed display, both documented.
- **power pull half** (`power.ts`, `power-ffi.ts`, `105_power.c`): `state` marks `available:false` instead of fabricating a battery reading; `idleSeconds` refuses a non-number with the native reason; a refused `sleepPrevent` returns `ok:false` with the C reason; a missing adapter returns `not-implemented` naming the platform API. The push half uses one observer object and idempotent `crust_power_watch`, so re-subscribing does not stack native observers, and the six listeners are keyed by kind rather than window — events are broadcast to all pages by design, so a closed window does not leave a per-window event channel.
- **theme/dock setters** (`theme.ts`, `dock.ts`): invalid appearance/value/label types throw `bad-request`; a refused `setAppearance:` or `setProgress` carries the C reason; `progress` is reported as `not-implemented` when the indicator cannot be installed; `bounce` treats request id `0` as valid and `-1` as the refusal sentinel.
- **shortcut trigger channel** (`shortcuts.ts`, `93_shortcuts.c`): one runtime class and one `JSCallback` per process; `onTrigger` returns an unsubscribe that only clears the current handler; foreign hotkey ids (signature mismatch) are ignored; `dispatch` is gated on an id this unit registered, so a page cannot fabricate a press.
