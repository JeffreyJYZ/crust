## HIGH — `crust build` embeds unvalidated extension exports, so one bad file kills the whole app at startup
- where: `src/cli/build.ts:105-133` passes `resolveExtensionFiles` (all files, existence check only) into `wrapperSource`; `src/extensions/entry-source.ts:35-41` pushes `import(...).default` with no validation; `:53` calls `registry.register(...(await extensionPlugins()))` outside every `try`; `src/plugins/registry.ts:22-26,27-32` throws on a non-plugin and on a duplicate name; applied at `src/runtime.ts:104-108`.
- mechanism: dev filters files through `loadExtensions` and passes only `extensions.loaded` (`src/cli/dev.ts:107,148`), which checks `isExtension` and duplicates (`src/extensions/load.ts:51-86,127-148`). Build never calls that loader: a file with no default export yields `undefined`, and two files with one name yield a duplicate — both compile fine, `build` prints "N files embedded" and exits 0, then `registry.register` throws before `startApp` opens a window. (A plain `definePlugin` export is also accepted where dev rejects it; that only crashes when its name is a core-reserved one.) The `try/catch` added to the generated imports covers import-time throws only, not registration.
- reachable by: any `crust build` project where `extensions/*.ts` has no default export or two files declare the same name. `measured`: generated entry pushes bare `.default`; `new PluginRegistry().register(undefined)` throws `register: not a plugin definition` and registering two `clock` definitions throws `plugin "clock" is already registered`. Under `crust dev` the same files are reported with file and reason and the window keeps running.
- smallest fix: call `loadProjectExtensions` in `build`, fail with `extensionErrorLines` on errors, and pass only `files` that `loadExtensions` validated (or make the generated entry filter with a shared `isExtension`/dedupe before `register`).

## MEDIUM — a native symbol named after a generated local emits a bindings module that cannot parse, so the command is silently absent
- where: `src/packaging/extension-names.ts:58-61` (`checkName` rejects only TS keywords and a regex); `src/packaging/extension-bindings.ts:76-105` emits `import { dlopen, FFIType }`, `import { join }`, `const DYLIB`, `let ffi`, `function open()`, `export function reload()` in the same module scope as `export const <symbol.name>`; `src/extensions/entry-source.ts:35-41` swallows the resulting import error with only `console.error`.
- mechanism: `open` is an ordinary POSIX C symbol; `checkName` accepts `open`, `reload`, `ffi`, `DYLIB`, `join`, `dlopen` and `FFIType`, but each collides with a binding the generator itself declares. The generated module is a syntax error, so its import throws; the generated entry catches and skips it, `registry.register` sees a shorter array, and the app opens with `unknown-plugin` for that command. Build still reports success. `arguments` is likewise accepted but illegal in a module's strict mode.
- reachable by: any project whose native extension exports one of those C symbols (for example a wrapper around POSIX `open`) and passes it as a `SymbolSpec` to `writeBindings`/`renderBindings`. `measured`: `renderBindings` output transpiled with `Bun.Transpiler` throws `"open" has already been declared`, and likewise for `reload`, `ffi`, `DYLIB`, `join`, `dlopen`, `FFIType`, and `Declarations with the name "arguments" cannot be used in strict mode`, while `checkName` accepts every one.
- smallest fix: reserve the generator's own identifiers (and strict-mode-only-illegal names like `arguments`) in `checkName` so `renderBindings` refuses at generation time with an actionable error instead of shipping an unparseable module.

## MEDIUM — a failed `reload()` closes the working dylib handle and leaves every command calling a closed library
- where: `src/packaging/extension-bindings.ts:84-96` generates `let ffi = open();` and `export function reload(): void { ffi.close(); ffi = open(); }`; the exported command wrappers at `:97-104` call `ffi.symbols.<name>(...)`.
- mechanism: `ffi = open()` evaluates the right-hand side first, so if the reopen throws — an ABI mismatch, a missing or half-written dylib during a rebuild — `ffi` keeps its old, already-closed value. Every subsequent command call dereferences a closed `Library`, so an operation that should have been a no-op failure bricks the extension for the life of the process. `extension-bindings-abi.test.ts:45-81` covers a successful reload and a mismatch at first import, but never a failed reload followed by a call.
- reachable by: an extension that calls the generated `reload()` after replacing its dylib with a different ABI (or before the write finishes). `measured`: the generated text is exactly `ffi.close(); ffi = open();`; `read`: the assignment semantics and the wrappers' `ffi.symbols` call site.
- smallest fix: open the replacement first into a local (`const next = open(); ffi.close(); ffi = next;`) so a failed reopen leaves the original handle intact.

## LOW — `renderBindings` accepts invalid FFI types and duplicate symbol names, emitting silently mis-bound or unparseable modules
- where: `src/packaging/extension-bindings.ts:59-62,97-104` indexes `FFI`/`ARGS`/`RETURNS` directly and joins with `", "`; `src/packaging/extension-names.ts:58-61` checks only name syntax.
- mechanism: `FFI[badType]` is `undefined`, and `[undefined].join(", ")` is the empty string, so a symbol whose argument type is mistyped emits `args: []` — the wrapper still passes its arguments, so `dlopen` binds a different signature than the source declared. `RETURNS[badType]` becomes `undefined` in both the spec and the TS return annotation. Two symbols with the same name produce duplicate `export const` declarations. None of these are refused at generation time; the ABI marker is unrelated and does not catch a wrong signature.
- reachable by: a project that builds its `SymbolSpec[]` from JSON or a cast (TS source literals are type-checked), with a typo such as `returns: "int"` or a copy-pasted duplicate name. `measured`: `renderBindings` with `args: ["int"] as never` emitted `add: { args: [], returns: undefined }` and `export const add = (a0: undefined): undefined => …`, and the text parsed; a duplicate `add` emitted a module `Bun.Transpiler` rejects with `"add" has already been declared`.
- smallest fix: in `renderBindings`, reject symbol names that repeat and every arg/return not present in `FFI`/`ARGS`/`RETURNS` with an actionable error before emitting code.

## Checked and clean
- Platform compile names and flags (`extension-compile.ts:40-72`, `extension-tools.ts:22-26,46-48`): `dylibSuffix` returns `.dll`/`.dylib`/`.so`, clang picks `-shared` off darwin, rust prefixes `lib` only off win32, and `toolFileNames` adds `.exe`/`.cmd`/`.bat`. The three platform defects in the older extensions report are fixed. `read`.
- FFI type projections (`extension-ffi.ts:18-50`): `FFI`, `RETURNS` and `ARGS` cover every `FfiType`/`FfiReturn`; `i64`/`u64` are `bigint`, `cstring` is `string | null`, `void` appears only as a return. `ARGS` has no `void`, so a void argument cannot be emitted. `read`.
- ABI marker and invoke path (`extension-bindings.ts:52-92`): `abiVersion` declares `crust_extension_abi` in the spec so `dlopen` resolves it at open, checks the value before returning, and command wrappers call `ffi.symbols.<name>` at call time rather than capturing a symbol. `extension-bindings-abi.test.ts:45-81` exercises a rebuild plus a mismatch. `read`; the failed-reload hole above is separate.
- Load-order determinism (`src/extensions/load.ts:97-113,60-84`): discovery sorts filenames before import, config names keep their order, and duplicate names refuse every claimant, so the registry table is stable and one file cannot shadow another. `read` plus the four load tests.
- Compile arguments are argv arrays, not a shell string (`extension-compile.ts:57-72`): file and output paths are separate arguments, so spaces or regex characters in a project path cannot be reinterpreted. `read`.
- `pgrepLiteral` (`extension-pattern.ts:9-12`) escapes every extended-regex metacharacter and `scripts/e2e-native.ts:43` applies it to both patterns before they reach `pgrep -f`. The older unescaped-host-path finding is fixed. `read`.
- Native dylibs not shipping in a compiled app is a documented limit of the example (`examples/native/README.md:40-41`), not a regression; build does not claim to place them. `read`.
- Re-checked from the older extensions report, still unfixed and not re-listed as new: swallowed `readdir` errors (`load.ts:106-108`), symlinked files skipped by discovery (`load.ts:102`), absolute config names not gaining `.ts` (`load.ts:121`), brand-only `isExtension` (`define.ts:49-54`), and the stale `renderExtensionImports` comment (`entry-source.ts:51-52`). `read`.
