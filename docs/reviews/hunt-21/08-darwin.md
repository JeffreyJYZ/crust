# Darwin platform hunt — 21 (lane 08)

Claim labels: `measured` = I ran a read-only extraction over the tree; `read` = source inspection.
No GUI app, e2e suite or cursor action was used. No Windows or Linux runtime claim is made.

## MEDIUM — two concurrent captures cross-talk: capture B resolves with window A's picture

- where: `src/platform/darwin/snapshot.ts:58-59` (`sink`, `listener`), `:122` (`pending`), `:125-129` (`supersede`), `:149-171` (`pending` / `setChannel`), `:172` (`take`); `src/platform/darwin/shim/123_snapshot.c:48-56` (one `shot_sink`, one `shot_png`), `:141-159` (`shot_invoke`), `:175-189` (`crust_shot_take`).
- mechanism: `takeSnapshot` keeps **one** module-level `pending` and installs **one** C sink. `supersede()` rejects the earlier JS promise, but it cannot cancel the earlier WebKit render. Both completions run through the same `shot_invoke`, which overwrites the single `shot_png` slot and calls the same sink. The listener installed for the *second* capture settles whatever `pending` currently is, and `settle` calls `shim.read()` on the shared slot. Whichever completion fires first settles the surviving promise, using that completion's picture.
- reachable by: `read` — page calls `window.capture("a")` and `window.capture("b")` in the same tick (or a window capture and a `browser.capture` overlap). `takeSnapshot(A)` installs pending A and sends a render of A; `takeSnapshot(B)` fails A's promise, installs pending B and sends a render of B. When A's WebKit completion lands, `shot_invoke` stores A's PNG and calls the sink, whose listener resolves B with `shim.read()` → A's PNG, A's width/height and A's scale. The caller asked for B and receives a picture of A. `window.capture` and `browser.capture` both route through `takeSnapshot` (`window-capture-adapter.ts:18`, `browser-ports.ts:69`), so the collision crosses the two plugin surfaces too.
- smallest fix: pass a capture id through the C sink (`shot_sink` takes `(id, ok)`) and have `shot_invoke` write into a per-id slot; ignore completions whose id is no longer the current `pending`. At minimum, capture the id in the JS listener and drop a sink call whose id does not match, so a superseded render can never settle a later promise.

## MEDIUM — the autorelease pool every shim unit relies on is never created or drained

- where: `src/platform/darwin/shim/50_app.c:39-49` (`shim_pool_new/init/drain`), `src/platform/darwin/index.ts:136-138` (declarations), `src/platform/darwin/shim/50_app.c:84-106` (`shim_pump`), `src/platform/darwin/platform.ts:71-74`, `src/platform/darwin/appkit.ts:8-38`.
- mechanism: several C units explicitly document that their `+0` objects are "left to the autorelease pool the pump drains" (`126_preview_data.c:6,25-26`), "autoreleased by the pool the caller already holds open" (`50_app.c:11`), or fetched as autoreleased objects per call (`97_screen.c:7-9`). The pump neither creates nor drains a pool, and neither does `start()`. `shim_pool_new`, `shim_pool_init` and `shim_pool_drain` are declared in `index.ts` but have **no call site anywhere in `src/`** (`measured`: `rg -n 'shim_pool|pool_drain|autorelease' src --glob '!*.test.ts'` returns only the declarations and comments). Autoreleased `NSDate`, `NSEvent` (one per pump tick), `NSString`, `NSNumber`, `NSData`, `NSImage`, `NSArray`, `NSValue`, `WKFindConfiguration` and preview items therefore accumulate for the whole process lifetime.
- reachable by: any long-running app. The pump calls `shim_pump` every tick (`pump.ts:40-46`), which builds `-date`, `-dateByAddingTimeInterval:` and `-nextEventMatchingMask:` objects (`50_app.c:90-99`) with no pool; repeated `preview.show`, `clipboard.readImage`, `opener.openPath`, `find.search`, `dock.setBadge` and `theme.set` add more. Memory grows without bound as a function of uptime, not of page-visible calls.
- smallest fix: create and drain an `NSAutoreleasePool` around each `shim_pump` tick inside C (`shim_pool_new/init` at entry, `shim_pool_drain` before each return), and either use the declared `shim_pool_*` exports at startup or remove them. Audit the units whose comments promise a drain so their `+0` objects are not kept past it.

## LOW — closing a browser surface leaks its NSView, WKWebView, configuration and both delegates

- where: `src/platform/darwin/browser.ts:80-87` (`newWebview`, `shim_browser_view_new`), `src/platform/darwin/browser-ports.ts:41-46` (`shim_webview_configuration()` per surface), `src/platform/darwin/browser-surface.ts:63-76` (`teardown`), `src/platform/darwin/shim/131_browser.c:50-77`, `src/platform/darwin/shim/132_browser_ui.c:112-121`, `src/platform/darwin/shim/107_navigation.c:169-193`.
- mechanism: `shim_webview_configuration` returns an alloc/init `+1` object; `shim_webview_new` and `shim_browser_view_new` each return an alloc/init `+1` object. `teardown` sends only `-removeFromSuperview` to the webview and its host view, which drops the superview's retain but not the original `+1`. `measured`: `rg -n 'release|autorelease' src/platform/darwin/browser*.ts src/platform/darwin/shim/13*.c` finds no release anywhere in the browser path. The UI delegate (`[cls new]` then `objc_setAssociatedObject(..., BR_RETAIN)`) and the navigation delegate (same pattern) each carry two retains; `crust_nav_uninstall` clears the association but never releases the `+1` from `new`, and there is no UI-delegate uninstall at all.
- reachable by: `browser.open` then `browser.close` (or the host window closing, which calls `teardown` via `SurfaceStore.mine` at `browser-surface.ts:53-60`). Repeating that cycle leaks one `WKWebViewConfiguration`, one `WKWebView`, one `NSView`, one `CrustBrowserUIDelegate` and one `CrustNavigationDelegate` per cycle. This is the browser surface that landed after hunt-20, so it is not covered by that report's leak finding.
- smallest fix: release the `+1` configuration after `shim_webview_new`, release the `+1` webview and host view after the detach sends, and add a UI-delegate uninstall that clears the association and releases the delegate's own `+1`. Balance `crust_nav_install`'s `[cls new]` with a `release` after the association retains it.

## LOW — `nativeWindow(label)` still hands out a pointer to a closed window (re-check, unchanged since hunt-20)

- where: `src/platform/darwin/windows.ts:82-85` (`native`), `src/platform/darwin/window-adapter.ts:16-25` (`require`), `:89-95`, `:104-114`.
- mechanism: unlike `handle()`, `webview()` and `labels()`, `native()` does no liveness check and no prune. After `window.close(label)` sends `-close` but leaves the entry in the map, `native(label)` still returns the `NSWindow *`. `setReleasedWhenClosed:0` (`window-create.ts:73`) keeps that object alive, so sends are memory-safe but act on a window no longer on screen; `setTitle` passes its own readback (`app` reads `-title` from the dead object, which still answers) and reports success.
- reachable by: `window.create("x")` → `window.close("x")` → `window.setTitle("x", "new")` / `window.focus("x")` / any `windowStateAdapter` or `windowChromeAdapter` command. `isOpen("x")` correctly reports false, so two commands disagree. `measured`: the `native()` body at `windows.ts:83-85` is byte-for-byte the shape hunt-20 quoted; still unfixed.
- smallest fix: have `require()` go through a liveness-checked accessor (or call `platform.window(label)` first), so geometry, focus, title and chrome commands on a closed label throw `unknown-window` the way `isOpen` reports `open:false`.

## LOW — PREFLIGHT still omits the selectors the JS sends and almost every C send (re-check, unchanged since hunt-20)

- where: `src/platform/darwin/preflight.ts:15-158` vs all send sites.
- mechanism: `startAppKit()` (`appkit.ts:10-16`) checks only entries in `PREFLIGHT`. A selector sent from JS but absent from the lists is guarded only at send time (`objc.ts:95-97`); one sent from C is guarded not at all in most units. The promise that a missing selector names itself at `start()` therefore holds only for the curated subset.
- reachable by: `measured`: I extracted every `S.<x>(r, "<sel>"…)` from non-test TS and every `sel_registerName("<sel>")` from all `.c` files under `src/platform/darwin` and diffed against `preflight.ts`. JS sends missing: `setTitlebarAppearsTransparent:` (`window-create.ts:129`, every material window), `configuration`, `userContentController`, `userScripts` (`content-world.ts:35-37`, every window with a token URL). C sends missing: **139 distinct selectors**, including the whole `shim_window_set_material` chain (`115_window_material.c:14-42`), `shim_app_set_icon` (`50_app.c:17-35`) and `shim_webview_new`'s `initWithFrame:configuration:` (`30_webview.c:31-32`). A system lacking one of these raises an uncaught ObjC exception → SIGABRT with no JS error, exactly the failure PREFLIGHT exists to replace. Still unfixed from hunt-20.
- smallest fix: add the four JS selectors to `PREFLIGHT`; for C-only selectors either add them to the internal lists where the class is stable or give each send the same `class_getInstanceMethod` null-check the liveness helpers use. Soften the "every selector" comments until the two sets match.

## LOW — `+1` Cocoa objects still never released in the shim's one-shot paths (re-check, unchanged since hunt-20)

- where: `src/platform/darwin/shim/50_app.c:13-37`, `src/platform/darwin/shim/40_window.c:25-36`, `src/platform/darwin/shim/115_window_material.c:19-42`, `src/platform/darwin/shim/121_content_world.c:16-24,54-75`.
- mechanism: each helper calls `alloc` plus an `init…` that returns `+1`, uses the object and never sends `release`. `NSVisualEffectView` is retained by `addSubview:` but keeps the extra `+1`; the `NSString` title/source/name and the `WKUserScript` objects leak outright. The download unit documents the rule (`downloads/00_prelude.c:67-73`) but the main shim does not follow it. `measured`: `rg -n 'release' src/platform/darwin/shim/*.c` shows no `release` sends in these four files; still unfixed from hunt-20.
- reachable by: every `app.icon` apply (startup), every `window.setTitle`, every material window, every `installContentWorldBridge` call (two scripts plus the isolated world name). Bounded by call count, but a page calling `window.setTitle` in a loop grows memory without bound.
- smallest fix: release each `+1` object immediately after the consuming send, as `dl_start`/`dl_file_url` already do.

## LOW — downloads: cancel before the completion lands is refused, and the 33rd live download goes untracked (re-check, unchanged since hunt-20)

- where: `src/platform/darwin/shim/downloads/30_api.c:67-88` (`dl_start`), `:91-101` (`dl_cancel`), `src/platform/darwin/shim/downloads/20_delegate.c:49-61` (`dl_start_done`).
- mechanism: `dl_start` mints the token and returns it immediately, but the `dl_downloads[slot]` entry `dl_slot(token)` needs is written later in the async completion. `dl_cancel` calls `dl_slot` and returns 0 until that entry exists, so it refuses the cancel. `dl_start_done` frees the block slot and decrements `dl_started_count` *before* calling `dl_free_slot()`; with all 32 download slots occupied it returns without storing the download or setting its delegate, so WebKit downloads it with no delegate and JS sees no events, progress or cancel. `dl_start` gates on `dl_started_count >= 32`, not on a free download slot, so a 33rd start is admitted.
- reachable by: `downloads.start(url)` then `downloads.cancel(id)` in the same tick → cancel returns false and the file still downloads. For the slot bug: start 32 downloads, let all reach their delegate, then start a 33rd → its completion finds no free slot and the adapter (`downloads.ts:135-157`) never learns about it. Still unfixed from hunt-20.
- smallest fix: keep a token→slot intent record at `dl_start` time (or queue cancels until the slot fills); gate `dl_start` on a free download slot; and in `dl_start_done`, refuse to consume the block slot when `dl_free_slot()` is `-1`.

## Checked and clean

- **FFI arity and width vs the C prototypes** — `measured`: I parsed all 279 `symbols:` declarations across 30 binding modules and matched each against its C definition, comparing arity and type width (`i32`/`i64`/`f64`/pointer). No genuine drift. The remaining diffs in my script are all typedef spellings (`obj_t`, `br_t`, `pv_t` = `void *`) and `const char *` return spellings that my parser classified as `i32`; each is declared `P` or `CS` on the TS side. `arity.test.ts` covers arity; my pass adds the width check it does not do. One near-miss worth naming: `shim_preview_set_paths` is `int len` in C and `I32` in TS — correct.
- **`bun:ffi` struct/BOOL widths at the send sites** — `read`: `shim/20_sends.c:25-58` reads BOOL returns as `char` and 64-bit returns as `long long`; `S.pq1`/`S.vq1` widen JS numbers to `BigInt` for `I64` (`objc.ts:117-120,147-150`); the colon sends pass an explicit nil `sender` with a three-parameter prototype (`92_window_state.c:55-86`); all rectangles and sizes are built on the C stack (`40_window.c:17`, `30_webview.c:26`, `131_browser.c:55`, `97_screen.c:47-51`). No drift found.
- **Tagged pointers / no object crosses bun:ffi** — `read`: no export returns an `NSString`, `NSNumber` or other ObjC object. Strings are built in C with `-initWithBytes:length:encoding:` and read back into C buffers or as `cstring` (`shim_window_title_utf8`, `crust_nav_url`, `tray_title_copy`, panel and download paths). The rule at `shim/10_prelude.c:2` is respected at every boundary I traced, including `crust_ax_*` and `crust_opener_*`.
- **Callback/trampoline lifetimes** — `read`: the JSCallbacks in `find.ts`, `menu-api.ts`, `status-bar-item.ts`, `downloads.ts`, `snapshot.ts`, `browser.ts`, `shortcuts.ts`, `power.ts`, `network-status.ts` and `network.ts` are held in module- or closure-level variables, so C's stored function pointer cannot outlive a collected callback. Each C unit registers one IMP/trampoline as its comments require. `tray_destroy` and `menu_api_target` keep the runtime target classes alive for the process (`60_teardown.c:1-3`, `98_menu_api.c:78-99`).
- **Delegates that outlive their webview/window** — `read`: `CrustNavigationDelegate`, `CrustMediaDelegate` and `CrustBrowserUIDelegate` are attached with `objc_setAssociatedObject(..., RETAIN_NONATOMIC)` *before* the unretained `-set*Delegate:` send, so the delegate cannot be collected while the getter may still reach it; `crust_nav_uninstall` clears the association. `shim_preview_owner_live` and the observer rely on `setReleasedWhenClosed:0` keeping the owner addressable after `-close`. The only lifetime defect found is the missing release reported above, not a use-after-free.
- **The pump and run loop** — `read`: pump is a non-rearming `setTimeout` chain (`pump.ts:34-48`) calling `shim_pump`, which drains one event per tick (`50_app.c:84-106`); `quit()` stops the pump before closing windows and calling `-terminate:` (`platform.ts:160-179`), so a re-entrant close cannot interleave with a tick. The missing autorelease pool above is the one defect on this axis.
- **Arity test coverage** — `read`: `arity.test.ts` walks every `.c` source under the directory recursively and every top-level binding module, asserts its parser saw `shim_window_new`, `shim_open_panel`, `shim_save_panel`, `shim_webview_load`, `shim_send_p0`, and checks cross-file arity conflicts. Its blind spot is type width, which my pass covered.
