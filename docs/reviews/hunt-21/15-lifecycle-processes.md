# Hunt 21 — app lifecycle & process supervision

All findings are `read` unless marked `measured`. No GUI launch, e2e suite or Windows/Linux runtime
observation was run, per the hunt contract. Predecessors `hunt-20/04-shell-sidecar.md` and
`hunt-20/15-lifecycle.md` were read first; their reported-and-fixed items (child reaping at quit,
`dropIfUnchanged` stale-lock takeover, `before-quit`/`will-quit` on the **window-all-closed**
watch) are not re-reported here.

## HIGH — `app.quit()` skips `before-quit` and `will-quit`, so save-on-quit work is lost on the quit path it owns
- where: `src/app.ts:177-190`, `src/app-frames.ts:23-35`, `site/app/docs/guides/lifecycle/page.mdx:11-14,34-36`, `site/public/SKILL.md:144`
- mechanism: (read) `App.quit()` calls `quitAfterSaving()` (which only saves the window frame), clears its watch intervals, `reapChildren("SIGTERM")`, then `flushLogger().finally(() => platform.quit())`. It never calls `emitOnQuit()` for `before-quit` or `will-quit`. The docs promise those events on quit ("An `await` inside it really does run before the process ends either way") and list `app.quit()` as "end the app"; the only quit path that emits them is `watchAllClosed` in `src/app-window-watch.ts:24-31`, which is a separate code path the explicit call does not go through.
- reachable by: (read) Any quit not initiated by the all-closed watch: a "Quit" menu item whose action is `app.quit()`, a command handler that calls `app.quit()`, or a delayed continuation that ends the app. Concretely, `app.on("before-quit", async () => await saveDraft()); menu.action = () => app.quit();` writes nothing — `saveDraft` never runs and the process exits. The shipped default template's `app.on("window-all-closed", () => app.quit())` (`src/cli/build/wrapper.ts:103`, `src/single-runner.ts:26`) is the one case where the framework's watch emits the events alongside the call; the tests in `src/app-quit-events.test.ts` register a `window-all-closed` listener that does **not** call `app.quit()`, so they never exercise the real template shape. Note also (read, not measured): on that template shape `app.quit()` starts `platform.quit()` from its own `flushLogger().finally()` while the watch's emit chain is still on microtasks, so a listener that awaits real work can be cut off by `process.exit(0)` — a probe that runs the actual `App` with the template listener and an async `before-quit` save would settle whether the watch chain always wins that race.
- smallest fix: route `quit()` through the same event sequence — emit `before-quit`, then `will-quit` via `emitOnQuit`, guarded against re-entry when `watchAllClosed` already emitted them — before `quitAfterSaving`/`platform.quit()`; add a test whose `window-all-closed` listener calls `app.quit()`.

## MEDIUM — the crash guard watches a pid by number only, so a recycled pid orphans it and can misattribute a crash
- where: `src/runtime-crash-guard.ts:42-50,153-159`, `src/child-reap.ts:20-31`, `src/app.ts:185-188`
- mechanism: (read) `watchCrashTarget` is `while (alive(target.pid)) await Bun.sleep(100)`, where `alive` is `kill(pid, 0)`. That cannot tell whether the still-live pid is the armed app. If the OS reuses the app's pid before the next 100 ms poll, the guard keeps watching a foreign process, exits only when that process ends, and then reads whatever crash record is present. The guard is spawned with `Bun.spawn` in `startCrashGuard` and is **not** passed to `trackChild`, so `app.quit()`'s `reapChildren("SIGTERM")` and the `process.on("exit")` SIGKILL pass never touch it; when the pid is reused it survives the app indefinitely as an orphan.
- reachable by: (read) App faults (record written, `_exit(70)`), the pid is recycled within one poll interval by any newly spawned process, and that process runs for a long time — the guard stays alive with a bridge and an owner that are gone, and any record it eventually reads is attributed to the wrong process lifetime. PID reuse within 100 ms is platform-dependent and was **not measured** here; the code has no identity token to prevent it. This is the recycled-pid class already reported for the single-instance lock in `hunt-20/15`; the guard is a different surface and was not covered there.
- smallest fix: pass a process start-time token (or a guard-owned launch id) and verify it before treating the pid as the target; register the guard with `trackChild` so `app.quit()` can signal it, or have `stop()` called from the quit path.

## LOW — `sidecar.kill` answers `ok: true` for a child that already exited
- where: `src/plugins/sidecar-commands.ts:89-115`, `src/plugins/sidecar-types.ts:88-91`, `src/plugins/shell.ts:174-183`
- mechanism: (read) `kill` looks the id up in `running`, calls `child.kill()` and returns `{ ok: true, id }`. The map is pruned only by `child.exited.then(finish)` (`sidecar-control.ts:88,92`), so between the child's exit and that microtask the id is still present. `child.kill()` on a departed process either no-ops or throws (`sidecar-kill-failed`), and in the no-op case the page gets a success for a signal that reached nobody. Shell does this correctly: `shell.kill` returns `{ ok: true, killed: false, id }` when `finished(record.child)`; `SidecarKilled` has no `killed` field, so the caller cannot tell.
- reachable by: (read) A declared sidecar exits on its own, and the page calls `sidecar.kill({ id })` before the `exited` handler prunes the entry — normal for a page that polls `list` and kills whatever it still sees. The same check applies to the 2 s grace timer at `sidecar-commands.ts:106-114`, which re-kills on an id that may already be finished.
- smallest fix: check `child.exitCode !== null || child.signalCode !== null` first, prune and return `killed: false`; add `killed` to `SidecarKilled` and to the timer's guard.

## Checked and clean
- Child reaping at quit and dev-restart SIGTERM: (read) `installReapOnExit()` runs once; `app.quit()` sends `SIGTERM` over the tracked set and the `process.on("exit")` pass escalates to `SIGKILL`; `registerShutdownSignals()` (`runtime.ts:41`) calls `process.exit(0)`, which drives that exit listener. `src/plugins/shell-reap.test.ts` and `sidecar-reap.test.ts` measure a stubborn child gone after both paths. No untracked shell or sidecar child found.
- Stale single-instance lock race: (read) `take()` uses `wx`/`O_EXCL`, `dropIfUnchanged()` re-reads the exact bytes before unlinking, and both waiters converge on one winner. `src/plugins/single-instance-stale.test.ts` forces the competing-writer interleave and asserts the fresh lock survives. The residual recycled-pid weakness of the lock itself was already reported in `hunt-20/15` and is not re-litigated here.
- Crash store growth: (read) `writeRecord()` appends one line, rewrites the single `last-crash.json`, then `rotateLog()` keeps the newest `MAX_CRASH_RECORDS = 200` lines; page message and stack are capped at `MAX_CRASH_CHARS = 8192`; the native record is a fixed 84 bytes. Every file is bounded, and both write halves share one layout and `0600` mode.
- Crash guard death after start: (read) `startCrashPart` refuses to arm when the guard is not running, and `crash-reporter` re-checks `guard.running()` on every command, so a guard that dies later makes `last`/`list`/`report` answer `not-implemented` instead of an empty list. The guard's own exit is therefore not silently reported as success.
- `before-quit` native deferral: (read) `watchLifecycle` calls `source.settle()` in `finally` for `before-quit`, so a throwing listener cannot leave AppKit waiting; `emitOnQuit` does the same for the all-closed path. Both are covered by `app-lifecycle.test.ts` and `app-quit-events.test.ts`.
- `attach`/`configure`/`deferBridge`/`run`/`use`/`command` post-start guards: (read) all mutators throw once `#started` is set and `run()` refuses a second call, so a second quit watch or bridge cannot be installed mid-run.
