# Wave 1 brief: the foundation the three features share

One lane, because every file here is one another lane would otherwise collide on. Nothing user-visible
ships in this wave; it exists so wave 2's three feature lanes touch disjoint files.

## What lands

1. **Three config sections**, each optional, each the opt-in for its feature:
   - `pty?: { shell?: string }` — an absent section means the pty plugin is never registered, because a
     page-reachable pty is command execution and must be declared, not inherited from a plugin list.
   - `preview?: { width?: number; height?: number }` — the panel's default size in points; absent still
     registers `preview`, it only refuses an empty one.
   - `browser?: { origins?: string[] }` — the `http(s)` origins an embedded surface may load; absent
     means the plugin registers and refuses every origin, so nothing loads by default.
   Validate each in the same place the other sections are validated, with a message naming the key.
2. **Registration**: `pty`, `preview` and `browser` join the built-in plugin names, wired in
   `src/runtime-plugins.ts` the way an existing native plugin is. The plugin modules do not exist yet —
   register behind a small named factory that wave 2 replaces, or leave the case returning `undefined`
   with a comment naming the wave. A name in the list that resolves to nothing must not reach the app as
   a registered command surface; say in the code which wave fills it.
3. **Capability vocabulary**: `pty:open` (never implied by `shell`), `preview:show`, `browser:open`.
   Grants stay per label; document each action's meaning in the capability list the docs already keep.
4. **Docs skeleton**: one page each under `site/app/docs/guides/` (`pty`, `preview`, `browser`) with the
   config block and "not implemented yet — ships in 0.2.9/0.2.10/0.2.11", plus `site/lib/nav.ts` entries.
   A page that promises nothing is fine; a page that promises a command that does not exist is not.

## Rules

- Own `src/config/types.ts`, the config validation module, `src/runtime-plugins.ts`, `site/lib/nav.ts`,
  and the three new guide pages. Nothing else, and no feature code.
- `rg`/`fd` only, `sd` never `sed`, no `bun fmt` without a path list, 200-line cap.
- Prove: config validation tests for each section (absent is valid, wrong type names the key), a
  registration test that `pty` absent means no pty commands and `pty: {}` means the surface exists or is
  refused with a named reason, and `bun check`, `bun run check:lines`, `site:build`, `check:links`.
- Push as `jyzbot`, open a PR, do not merge. Report under 12 lines, listing each file you created.
