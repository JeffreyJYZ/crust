# Wave 3 briefs: parity — Windows and Linux browser, Windows preview

By now darwin has an embedded browser and a QuickLook panel, and the pty works on POSIX. This wave makes
the browser work on Windows and Linux, and gives Windows a preview host. Linux preview stays a named
refusal, because no system preview API exists there — that is a fact to document, not a gap to fake.

Each lane owns its platform directory; shared files (`src/runtime-plugins.ts`, `src/config/types.ts`,
`plugins/browser.ts`, `plugins/preview.ts`) are read-only for wave 3. Where a shim unit must be added,
the lane owns that file and its preflight entry, and no two lanes edit the same C file.

## A — Windows browser (the expensive one)

The Windows shim is a singleton today: one `g_web` (`shim/42_webview.c:12`) and `shim_webview_navigate`
takes no handle, and the environment is created once (`shim/32_env.c:39-49`). A second surface needs:

- a controller table keyed by an integer handle, with every webview call taking that handle; the existing
  app window becomes entry 0 so no call site changes meaning;
- one `WebView2` environment per process, but a controller per surface, each with its own
  `ICoreWebView2Controller` and `put_Bounds` for positioning;
- settings on the child controller that keep it a viewer: no devtools, no autofill, `AreDefaultContextMenusEnabled`
  false unless the app asks, and the same capture denial the app window installs;
- `browser.*` commands routed to the same plugin API darwin already exposes, so the page sees one command
  set on every platform.

Proof runs on a Windows runner, not locally: a workflow job that loads a `Bun.serve` page in an embedded
surface, reads `state` (title), moves it, and captures the window. Reuse the shape of
`windows-arm-runtime.yml`; do not add a second copy of the resize proof.

## B — Linux browser

WebKitGTK gives one child per `GtkWindow` today (`shim/40_window.c:95-101`) and the load state is one
process-wide slot (`shim/30_webview.c:38-43`). Needed:

- a `GtkFixed` (or `GtkOverlay`) container inside the window's box so a child webview can be positioned by
  points, with the app's own webview at index 0;
- load-state keyed by the same handle the commands use, so `state` answers for the right surface;
- the same origin allowlist and `target=_blank` refusal as darwin.

Proof runs on the ubuntu gate with a real X server (the Linux e2e already launches a GTK app): open a
local page, read its title, move it, screenshot through `window.capture`.

## C — Windows preview host

No equivalent of `QLPreviewPanel`; the real API is the shell preview handler —
`IPreviewHandler` (`CoCreateInstance` from the file's `IPreviewHandlerFactory`, `SetWindow`, `SetRect`,
`DoPreview`), hosted in a child HWND over the app window.

- `preview.show` on Windows creates that host HWND, sizes it, and hands it the file; `preview.hide`
  destroys it. The COM apartment is the app's existing STA (recon measured `CoGetApartmentType` 0).
- Every failure path answers a named reason (`no-handler`, `preview-failed`, `not-a-file`), never a blank
  window; a file type with no registered handler is common, and the page must be able to say so.
- Proof on a Windows runner with a file whose handler is built in (`README.md` previews through the
  text handler; a `.png` through the image handler). Capture the window and show the host HWND exists.

## D — Linux preview: documentation only

`preview.show` answers `not-implemented` with the reason: no embedded system preview API exists on
Wayland/X11 without depending on a desktop environment's service. `opener.show` remains the way to open a
file in its own app. The guide for `preview` must state that plainly instead of implying parity.

Shared rules: `rg`/`fd` only, `sd` never `sed`, no `bun fmt` without a path list, 200-line cap, push as
`jyzbot`, open a PR, do not merge. Reports name the CI run URL for anything that can only be proven on a
Windows or Linux runner.
