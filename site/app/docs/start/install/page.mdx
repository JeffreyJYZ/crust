# Install

Five ways in: a release binary, Homebrew, a Bun global install, a checkout, or a tagged `bunx`. Every one needs a working
`bun --version`. Installing crust needs nothing else — no SDK, and no native artifact is built at
install time. Building a macOS app is the step that wants the Xcode command line tools, for
`codesign`.

## Download a binary

Six files — x64 and arm64 on each of macOS, Linux and Windows — built by the release workflow and attached to the tag that names it:

| platform              | file                                  |
| --------------------- | ------------------------------------- |
| macOS, Apple silicon  | `crust-<version>-darwin-arm64`        |
| macOS, Intel          | `crust-<version>-darwin-x64`          |
| Linux, x86_64         | `crust-<version>-linux-x64`           |
| Linux, arm64          | `crust-<version>-linux-arm64`         |
| Windows, x86_64       | `crust-<version>-windows-x64.exe`     |
| Windows, arm64        | `crust-<version>-windows-arm64.exe`   |

**[Get the newest release →](https://github.com/JeffreyJYZ/crust/releases/latest)** — the release page
lists the version, so no number here can go stale. The file is self-contained: the framework sources
are embedded, and `init`, `doctor`, `dev`, `build` and `package` all run from it on a machine that has
Bun and nothing else.

```sh
chmod +x crust-*-darwin-arm64
./crust-*-darwin-arm64 init my-app
cd my-app && bun install && ./crust-*-darwin-arm64 dev
```

A binary is not signed with a Developer ID, so macOS quarantines a downloaded one:
`xattr -dr com.apple.quarantine ./crust-*` clears it. Windows may show SmartScreen for the same
reason; there is no certificate to avoid it. Linux needs the GTK3 and WebKitGTK packages listed on
the [platforms page](/docs/reference/platforms).

**There is no npm package, and there is not going to be one.** `crust` in the root `package.json` is a workspace name, `crust init` pins the dependency as `link:<the checkout that ran init>`, and the `crust` name on npm belongs to an unrelated 2020 package — so `bun add crust`, `npm i -g crust`, and `bunx crust` outside a scaffolded app all fetch that stranger.

A global install is the one that looks like those and is not. `bun add -g crust` is the stranger above; `bun add -g github:JeffreyJYZ/crust#<tag>` names the repository, so it installs this CLI from that tag and nothing else. The bare name and the `github:` specifier are different packages, and only the second one is crust.

  <TabPanel label="Homebrew">

```sh
brew install JeffreyJYZ/tap/crust
crust --version                 # 0.2.13
```

macOS only — the formula declares `depends_on macos: :ventura`, so on Linux or Windows use a [release binary](#download-a-binary) instead. It is a source install for darwin: the tree lands in `/opt/homebrew/Cellar/crust/<version>/libexec/`, and `/opt/homebrew/bin/crust` execs the brewed `bun` on it. The formula tracks the newest tag, so a brewed `crust` is that release rather than `main`.

  </TabPanel>
  <TabPanel label="Bun global">

```sh
bun add -g github:JeffreyJYZ/crust#v0.2.13
crust --version                 # 0.2.13
```

The same tag `bunx` resolves, installed once instead of cached per run: `~/.bun/bin/crust` is a symlink into `~/.bun/install/global/node_modules/crust`, so `crust` answers anywhere — inside a scaffolded app or outside one. Upgrade by naming a newer tag (`bun add -g github:JeffreyJYZ/crust#v0.2.13` replaces that symlink); a non-default `BUN_INSTALL` prefix moves both `bin/` and `install/global/` under it.

  </TabPanel>
  <TabPanel label="From a checkout">

```sh
git clone https://github.com/JeffreyJYZ/crust
cd crust
bun install                     # two dev dependencies: @types/bun, vite
bun run start init my-app
cd my-app && bun install
bun run dev                     # the template's own script: crust dev
```

`bun run start` is `bun run src/cli/index.ts`, so it takes every command and flag the binary does. No scaffold wanted? `bun run start dev --dir examples/hello` runs the hello example straight out of the checkout.

A scaffold made from a checkout pins `crust` as `link:<checkout>`, so an edit under `src/` reaches the app without republishing.

  </TabPanel>
  <TabPanel label="Standalone executable">

```sh
bun run build:standalone        # writes dist/crust
./dist/crust init my-app
cd my-app && bun install && ./dist/crust dev
```

One file with the framework sources embedded — `src/`, `templates/`, `tsconfig.json`, `package.json` — so it needs no checkout at all: `init`, `doctor`, `dev` and `build` all run from it, on a machine with nothing installed but Bun. (On macOS `build` and its `--sign` stage still want the Xcode command line tools for `codesign`; Linux and Windows builds sign nothing.) This is the same file the [release page](https://github.com/JeffreyJYZ/crust/releases/latest) attaches per platform; building it yourself is how you get one for a target the workflow does not ship.

## A tag, without cloning

```sh
bunx github:JeffreyJYZ/crust#v0.2.13 init my-app
cd my-app && bun install
bun run dev
```

`bunx` resolves the specifier, caches it, and runs the binary out of the cache — no `PATH` entry, no global install. Inside the scaffolded app, `bun run dev` runs the copy the app pinned.

### The cache trap

`bunx` keys its cache on the specifier string, so a bare `github:JeffreyJYZ/crust` keeps serving whatever commit it first resolved. A stale entry answers an old version — and sometimes refuses a flag you know exists:

```
$ bunx github:JeffreyJYZ/crust init my-app --next
crust: unknown option --next
run "crust --help" for usage
```

Name a tag. `#v0.2.13` is the one specifier whose answer cannot drift, because the commit it names does not move. Or clear both cache directories:

```sh
rm -rf ~/.bun/install/cache/.bunx-501/crust@github@*
rm -rf ~/.bun/install/cache/@GH@JeffreyJYZ-crust-*
```

`#main` is not a cure: a moving name with a frozen cache entry in front of it fixes nothing.

## Which crust runs

`crust init` writes `crust` into the app's `package.json` and `bun install` links that copy as `node_modules/.bin/crust`. The specifier depends on where `init` ran: from a checkout it is `link:<the CLI's own tree>` (an edit under `src/` reaches the app without republishing); from a release it is the pinned tag `github:JeffreyJYZ/crust#v<version>`, so `bun install` fetches the exact version you asked for rather than whatever `main` is that week. Inside the project bun prefers the local binary, so **the app runs the copy it pinned** — the same files the CLI ran from, not a second download. Ask it directly with `./node_modules/.bin/crust --version`.

That `link:` is the other reason there is no npm package: it makes `import "crust"` in the app and the CLI one realpath, so both share a single `app` singleton. An installed crust would give a project two copies — the CLI's and its own — each with its own singleton, and a command registered by `main.ts` would be invisible under `crust dev`, which answers `crust: unknown command "greet"`.

Outside a project the question is `PATH` order. A Bun global install lives in `~/.bun/bin`, which sits earlier than `/opt/homebrew/bin`, so on a machine with both the bun copy answers `crust` and the brewed binary is shadowed. Homebrew reports that in its own caveats rather than failing:

```
The following crust executables are shadowed by commands in ~/.bun/bin:
crust
Running these by name will not invoke the version provided by Homebrew
because the shadowing commands come earlier in your PATH.
```

`which -a crust` prints every copy in the order they would be found, and `crust --version` — or `readlink "$(command -v crust)"` — says which one answered. Upgrading one does not upgrade the other: `bun add -g github:JeffreyJYZ/crust#<newer tag>` moves only the bun copy, `brew upgrade crust` only the brewed one, and neither touches a project's pinned `node_modules/.bin/crust`.

## When it does not work

```sh
crust doctor
```

It prints one line per check — platform, Bun, config, shim compiling, bridge binding and answering, dev port, dev URL, backend entry, window module, assets, templates, bundle — and exits 1 if any failed. A built app that opens here and is "damaged" elsewhere is the ad-hoc signature plus quarantine: `xattr -dr com.apple.quarantine "my-app.app"`.
