# Install

Three ways in. Every one needs **macOS 13 (Ventura) or later on Apple silicon** and a working `bun --version`. Nothing else — no Xcode, no command line tools, no SDK, and no native artifact is built at install time.

## Homebrew

```sh
brew install JeffreyJYZ/tap/crust
crust --version                 # 0.1.16
```

A source install: the tree lands in `/opt/homebrew/Cellar/crust/<version>/libexec/`, and `/opt/homebrew/bin/crust` execs the brewed `bun` on it. The formula tracks the newest tag, so a brewed `crust` is that release rather than `main`.

## bunx, with nothing installed

```sh
bunx github:JeffreyJYZ/crust#v0.1.16 init my-app
cd my-app && bun install
bunx crust dev
```

Needs Bun and nothing else. `bunx` resolves the specifier, caches it, and runs the binary out of the cache — no `PATH` entry, no global install.

## From a checkout

```sh
git clone https://github.com/JeffreyJYZ/crust
cd crust
bun install                     # two dev dependencies: @types/bun, vite
bun run start init my-app
```

`bun run start` is `bun run src/cli/index.ts`, so it takes every command and flag the binary does. A scaffold made from a checkout pins `crust` as `link:<checkout>`, so an edit under `src/` reaches the app without republishing.

## The one trap: the bunx cache

`bunx` keys its cache on the specifier string, so a bare `github:JeffreyJYZ/crust` keeps serving whatever commit it first resolved. A stale entry answers an old version — and sometimes refuses a flag you know exists:

```
$ bunx github:JeffreyJYZ/crust init my-app --next
crust: unknown option --next
run "crust --help" for usage
```

Name a tag. `#v0.1.16` is the one specifier whose answer cannot drift, because the commit it names does not move. Or clear both cache directories:

```sh
rm -rf ~/.bun/install/cache/.bunx-501/crust@github@*
rm -rf ~/.bun/install/cache/@GH@JeffreyJYZ-crust-*
```

`#main` is not a cure: a moving name with a frozen cache entry in front of it fixes nothing.

## Which crust runs

`crust init` writes `crust` into the app's `package.json`, and `bun install` links that copy as `node_modules/.bin/crust`. Inside the project bun prefers the local binary, so **the app runs the copy it pinned**, not the CLI you scaffolded with.

Both report the same version number and can be different commits. When an app behaves differently from the CLI, run `bunx crust --version` and `crust --version` in the same directory — the resolved commit, not the number, is the tell.

## When it does not work

```sh
crust doctor
```

It prints one line per check — platform, Bun, config, shim compiling, bridge binding and answering, dev port, dev URL, backend entry, window module, assets, templates, bundle — and exits 1 if any failed. A built app that opens here and is "damaged" elsewhere is the ad-hoc signature plus quarantine: `xattr -dr com.apple.quarantine "my-app.app"`.
