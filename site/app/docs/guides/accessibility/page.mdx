# Accessibility

Whether this process may drive the accessibility API, the one system prompt that grants it, and a count of the app's own window's AX children. Registered by the macOS runtime with `darwinAccessibilityAdapter()`.

This is about the **AX API** — reading and driving other apps. It is not about whether crust's own windows expose an accessibility tree; that is a property of the webview and the native window, and `elementCount` is the only thing here that touches it.

## Commands

| command        | arguments | answer                                  |
| -------------- | --------- | --------------------------------------- |
| `trusted`      | none      | `{ ok: true, trusted }`                 |
| `prompt`       | none      | `{ ok: true, trusted, prompted: true }` |
| `elementCount` | none      | `{ ok: true, count }`                   |

## Trust

```ts
const { trusted } = await window.crust.invoke("accessibility", "trusted");
```

A read: it never raises a dialog. Use it before a call that needs the API, so the app can explain itself instead of failing opaquely.

```ts
const { trusted, prompted } = await window.crust.invoke("accessibility", "prompt");
```

`prompt` raises the one system dialog that grants trust and answers the state after it. A human answers that dialog, so `trusted: false` is the common result of the first call. `prompted` is always `true` — it records that the dialog was raised, not that it was accepted.

## Counting the app's own tree

```ts
const { count } = await window.crust.invoke("accessibility", "elementCount");
```

The walk starts at the app's own AX element and counts the children of its first window. A window with no children answers `count: 0`, which is a real answer.

Two states are not a count, and both answer `not-implemented` rather than `0`:

| `requires`                      | meaning                                           |
| ------------------------------- | ------------------------------------------------- |
| `NSWindow`                      | no window is up yet, so there is no tree to count |
| `AXUIElementCopyAttributeValue` | the AX API refused the walk                       |

A count of zero from a window that does not exist is not evidence of anything, which is why the two are separated.

## A window is in AX only when the app is active

AppKit lists only windows on the **active Space**, and a window joins that Space only when its app is active. `-[NSApplication activate]` is silently refused for a process LaunchServices did not launch — which is how `crust dev` and the parity harness run — so a window can be visible, clickable and absent from `AXWindows` for every other process while `AXIsProcessTrusted` is true.

crust therefore sends `-activateIgnoringOtherApps:` when the app is not already active, guarded on `isActive` so creating a second window does not pull the app forward. `app.activate` decides when that happens: `"always"` (the default) on every window create, `"first"` only for the first window create of the process, and `"never"` not at all.

`isActive` alone cannot express `"first"`: it is false whenever the human is in another app, so a window created by the page would pull the app back in front. Measured on a built bundle with `lsappinfo info -only name $(lsappinfo front)` — front was `Activation crust` at t1.5 for the driver window, `Ghostty` at t3 after focus was handed away, and `Activation crust` again at t8 for a window the page created; a control run with window creation disabled showed no transition. `"first"` therefore uses one process-wide flag, and the cost is that a later window created while the app is inactive stays out of `AXWindows` until the user clicks the app — the same symptom `"never"` has for every such window. Measured on one window from a separate trusted process:

```
before  external=windows:0,children:-1,status:0
after   external=windows:1,children:4,status:0
```

So a zero is not by itself proof that the tree is missing: check `trusted` first, then whether the app is active. The gate is activation, not the window.

## Failure shape

Without an adapter — every platform but macOS — each command answers `not-implemented` with `requires: "AXIsProcessTrusted"`.

## Limits

The walk reads the app's own element only. Reading another process's tree needs `trusted: true` and code this plugin does not ship.
